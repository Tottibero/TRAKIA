# HC-01-05d — Seguridad HTTP

## Identificación

- **Bloque:** HC-01 — Infraestructura
- **Estado:** completada
- **Rama:** `chore/hc-01-infrastructure`

## Especificación aprobada

### Objetivo

Completar las protecciones HTTP necesarias para utilizar autenticación mediante cookies.

### Alcance

- Validar `Origin` en solicitudes que modifican estado, incluido login; rechazar `Origin` ausente en operaciones de navegador. Cualquier cliente legítimo sin ese encabezado requiere una excepción explícita, limitada y segura.
- Configurar una lista explícita de orígenes permitidos.
- Aplicar protección CSRF complementaria a `SameSite`.
- Limitar login a 5 intentos por minuto e IP y responder HTTP 429 al excederlo.
- Definir proxies confiables y derivar la IP real solo de cabeceras añadidas por ellos; ignorar cabeceras no confiables.
- Configurar CORS restrictivo con credenciales solo para orígenes permitidos y verificar preflight.
- Revisar atributos de cookies en desarrollo y producción.
- Documentar la configuración requerida para servir frontend y API bajo un mismo origen visible.

### Exclusiones

Redis, CAPTCHA, OAuth y gestión avanzada de sesiones.

### Dependencias

HC-01-05c. Esta tarea endurece las rutas y cookies ya definidas en HC-01-05c, sin cambiar sus contratos funcionales.

### Archivos o módulos afectados

Configuración y middleware/guards HTTP transversales de `apps/api/src/`; módulo de autenticación y configuración de cookies; documentación de desarrollo/despliegue aplicable; pruebas HTTP de seguridad.

### Criterios de aceptación

1. Un origen no autorizado se rechaza y las operaciones de navegador no aceptan solicitudes inseguras por omitir `Origin`; cualquier excepción está explícitamente acotada.
2. Las solicitudes legítimas del mismo origen funcionan y login está protegido frente a CSRF.
3. El límite devuelve 429 tras cinco intentos por minuto por IP.
4. La IP no puede falsificarse mediante cabeceras no confiables.
5. CORS no permite orígenes arbitrarios con credenciales y los preflight válidos siguen funcionando.
6. Los atributos de cookie son seguros en desarrollo y producción.
7. Guard y endpoints de HC-01-05c mantienen su funcionamiento.

### Pruebas previstas

Casos HTTP positivos y negativos para orígenes ausentes/no permitidos, CSRF, rate limiting, IP detrás de proxy confiable/no confiable, cookies y preflight CORS.

## Ejecución y resultados

Se añadió middleware transversal que exige un `Origin` permitido y el encabezado `X-TRAKIA-CSRF: 1` en solicitudes que modifican estado, limita login a cinco intentos por minuto según `request.ip` y devuelve 429 con `Retry-After`. Express solo confía en las IP/CIDR indicadas en `TRUSTED_PROXIES`. CORS valida orígenes HTTP(S) explícitos, permite credenciales y limita métodos y encabezados; se documentó el proxy de producción para servir web y API bajo un origen visible.

### Resumen de implementación

Se mantienen las rutas y contratos de HC-01-05c. Los clientes sin `Origin` no tienen excepción: también deben proporcionar un origen permitido y el encabezado CSRF.

### Desviaciones justificadas

El rate limit usa memoria del proceso y no comparte contadores entre réplicas; Redis está excluido por la especificación. Configurar `TRUSTED_PROXIES` incorrectamente o permitir que el proxy conserve cabeceras reenviadas del cliente puede afectar a la IP derivada; la configuración de despliegue debe limitarse a proxies controlados.
