# HC-01-05b — Comandos administrativos de autenticación

## Identificación

- **Bloque:** HC-01 — Infraestructura
- **Estado:** completada
- **Rama:** `chore/hc-01-infrastructure`

## Especificación aprobada

### Objetivo

Crear el primer usuario y recuperar su acceso mediante comandos administrativos sin endpoints públicos.

### Alcance

- Añadir `pnpm auth:bootstrap` y `pnpm auth:reset-password`, reutilizando la configuración de conexión TypeORM existente.
- Solicitar email, contraseña y confirmación interactivamente; ocultar la contraseña y validar email y política de contraseña.
- Limitar el bootstrap a una instalación sin usuarios y protegerlo frente a ejecuciones concurrentes mediante coordinación atómica en PostgreSQL.
- El reset reemplaza el hash e incrementa `sessionVersion` para invalidar sesiones activas.
- Ofrecer una vía no interactiva puntual para entornos sin terminal: recibir secretos por entrada estándar (stdin), sin pasarlos como argumentos CLI ni escribirlos en logs o Git; validar el formato y fallar de forma cerrada si faltan datos.
- Fallar con mensajes claros y sin revelar secretos. Ningún comando se ejecuta al iniciar NestJS ni durante las migraciones.

### Exclusiones

Endpoints HTTP, JWT, email de recuperación y registro público.

### Dependencias

HC-01-05a.

### Archivos o módulos afectados

Scripts de `apps/api/` o `scripts/` y comandos del `package.json` raíz; integración con `UsersModule` y conexión TypeORM existentes; pruebas administrativas aisladas.

### Criterios de aceptación

1. Bootstrap crea el primer usuario y una segunda ejecución no sobrescribe credenciales ni crea otro usuario.
2. Ejecuciones concurrentes no pueden crear usuarios adicionales.
3. Reset cambia el hash e incrementa `sessionVersion`.
4. Los errores de configuración y operación son claros y no incluyen contraseñas.
5. Los secretos no aparecen en logs, argumentos de proceso ni archivos versionados.
6. Los comandos solo afectan la base configurada para la ejecución y nunca se lanzan automáticamente.
7. En producción gestionada existe una forma segura y documentada de ejecutar el comando sin terminal.

### Pruebas previstas

Bootstrap inicial, repetición, concurrencia, reset y revocación por versión, configuración inválida, entrada stdin sin eco/log y ejecución en base PostgreSQL aislada.

## Ejecución y resultados

### Resumen de implementación

`auth-admin.mjs` quedó como adaptador CLI: recoge y valida entrada y obtiene `UsersService`/`PasswordService` mediante un contexto NestJS de `AppModule`. Bootstrap transaccional con advisory lock y reset de hash/version viven en `UsersService`, propietario de `User`; no se añadieron endpoints ni operaciones duplicadas de autenticación.

Seguimiento del fallo reportado en HC-01-05e: NestJS abortaba el proceso durante errores de inicialización, antes de que el `catch` del CLI pudiera informar. El entorno host revisado no tenía `DATABASE_URL`; `.env.docker` aporta solo las variables `POSTGRES_*` y no se carga automáticamente al ejecutar el comando raíz. La ejecución TTY con entradas sintéticas reprodujo la salida silenciosa. TypeORM sí conectó desde el host a `trakia_dev` con un `SELECT current_database()` read-only; la tabla `users` de esa base no está migrada. No se leyó ni modificó ningún usuario de desarrollo.

La corrección usa un contexto NestJS administrativo aislado (sin `AuthModule` ni dependencia de `JWT_SECRET`), desactiva `abortOnError` para permitir el manejo controlado, traduce errores de configuración/conexión a mensajes seguros y pausa stdin al limpiar los prompts ocultos. Se mantienen intactos `UsersService`, la transacción, el advisory lock y ambos comandos.

### Pruebas ejecutadas y resultados

Superadas con Node 26.13.0 y pnpm 12.19.0: `pnpm check` (lint, formato, typecheck, reglas arquitectónicas con fixtures positivas/negativas, 22 unitarias y build), `pnpm test:integration` y `git diff --check`. La integración verificó `current_database() = trakia_test`; migraciones al día, pruebas de usuarios y health superadas. El nuevo escenario CLI pasó bootstrap, repetición, reset/hash Argon2id, versión de sesión, errores y dos bootstraps concurrentes (códigos 0/1, un usuario). Las salidas no incluyeron los secretos sintéticos. El runner conservó sus variables de conexión saneadas. La verificación final confirmó `trakia_test` con cero usuarios.

Seguimiento del fallo: `pnpm test:integration` volvió a pasar en `trakia_test`, incluida la regresión de inicialización con `DATABASE_URL` ausente (exit code 1, sin señal de aborto, error útil y sin secretos). Pasaron bootstrap, rechazo por usuario existente, reset, validación y concurrencia. La prueba TTY manual mostró las contraseñas sin eco y terminó con mensaje seguro/código 1; no se accedió a datos de `trakia_dev`. El `pnpm check` actualizado pasó con Node 26.13.0 y pnpm 12.19.0 (32 pruebas unitarias y build); `trakia_test` quedó con cero usuarios sintéticos.

Inspección inicial del primer bootstrap real, solo lectura: la conexión TypeORM del host confirmó `current_database() = trakia_dev`; `typeorm_migrations` existía, `InitialTechnicalMigration1794355200000` estaba aplicada y `CreateUsers1794441600000` pendiente. En una comprobación posterior de solo lectura, `trakia_dev` ya tenía ambas migraciones aplicadas, la tabla `users` existía y contenía una fila. Solo se leyó el recuento, no datos personales; no se ejecutaron escrituras durante esas inspecciones.

**Prueba manual del propietario en Chrome con los servicios reales de Docker y PostgreSQL:** bootstrap del primer usuario en `trakia_dev`, login, persistencia de sesión al recargar, logout y redirección al login al abrir una ruta protegida sin sesión. Es evidencia manual comunicada por el propietario, no una prueba E2E automatizada ni una ejecución de Codex.

### Incidencias y riesgos pendientes

La prueba CLI se protege y falla antes de escribir si `trakia_test` no está vacía; la ejecución registrada usó una tabla vacía y limpió solo sus filas sintéticas. El flujo real en navegador fue verificado manualmente por el propietario; no hay una prueba E2E automatizada del frontend.

El procedimiento para migrar y ejecutar el bootstrap desde el host está en [development.md](../../development.md). La comprobación actual muestra que no quedan migraciones pendientes y ya existe una fila en `users`; no repitas el bootstrap sin confirmar primero el estado y la necesidad operativa.

### Revisión y aceptación

- **Resultado:** correctivo aceptado y tarea completada por autorización explícita del propietario mediante la solicitud de commit de HC-01-05b.
- **Evidencia de revisión y aprobación:** `pnpm check`, regresión e integración en `trakia_test`, auditoría arquitectónica sin hallazgos bloqueantes y prueba manual real del propietario documentadas arriba.

### Revisión arquitectónica

- **Resultado:** sin hallazgos bloqueantes ni recomendaciones.
- **Hallazgos y resolución:** el contexto `AuthAdminModule` compone únicamente `DatabaseModule` y `UsersModule`; `UsersService` conserva la propiedad de persistencia y sus operaciones transaccionales. El grafo no introduce ciclos ni imports de internos entre módulos. El contexto aislado está justificado porque el CLI no debe inicializar controladores/guardas HTTP ni depender de JWT. La verificación automática `pnpm architecture:check` pasó además de esta revisión manual.
