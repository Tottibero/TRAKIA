# HC-01-05c — Autenticación JWT y API

## Identificación

- **Bloque:** HC-01 — Infraestructura
- **Estado:** pendiente
- **Rama:** `chore/hc-01-infrastructure`

## Especificación aprobada

### Objetivo

Implementar las operaciones de autenticación privada del backend y proteger por defecto las rutas HTTP.

### Alcance

- Crear `AuthModule` y contratos Zod de autenticación en `packages/contracts`.
- Implementar `POST /api/auth/login`, `POST /api/auth/logout` y `GET /api/auth/me`.
- Instalar un guard global con excepciones públicas explícitas; mantener público `GET /api/health`.
- Emitir JWT firmado con duración de 12 horas y claims `sub`, `sessionVersion`, `iat`, `exp`, `iss`, `aud`; validar firma, algoritmo permitido, expiración, emisor y audiencia.
- Exigir y validar desde configuración el secreto de firma.
- Usar cookie HttpOnly, `SameSite=Lax`, `Path=/`, sin `Domain`, duración coherente con JWT y `Secure` en producción. Usar prefijo `__Host-` en producción cuando sea aplicable.
- Logout incrementa `sessionVersion` y elimina la cookie; en cada petición protegida se comprueba la versión vigente para revocar tokens anteriores.
- Responder genéricamente ante credenciales inválidas. `/auth/me` expone únicamente `id` y `email`.
- Configurar sesión sin guardar JWT en almacenamiento del navegador.

### Exclusiones

Protección CSRF definitiva, rate limiting, frontend y despliegue público. El backend no se considera apto para exposición pública hasta completar HC-01-05d.

### Dependencias

HC-01-05a y HC-01-05b.

### Archivos o módulos afectados

`apps/api/src/modules/auth/`, configuración transversal de API y guardas; `packages/contracts/src/`; pruebas unitarias de JWT/sesión e integración HTTP. Consumir usuarios mediante la capacidad pública de `UsersModule`.

### Criterios de aceptación

1. Login válido establece la cookie y login inválido responde sin revelar si existe el usuario.
2. `/auth/me` devuelve únicamente `id` y `email`; rutas privadas rechazan solicitudes no autenticadas.
3. `/api/health` continúa siendo público.
4. JWT expirados, alterados o con algoritmo/emisor/audiencia incorrectos se rechazan.
5. Logout invalida el token anterior y las demás sesiones del usuario mediante `sessionVersion`.
6. Secreto y tokens no aparecen en logs ni respuestas JSON.
7. Rutas y contratos respetan ADR-015 y los contratos compartidos permanecen independientes de NestJS y TypeORM.

### Pruebas previstas

Unitarias de validación JWT y versión de sesión; integración HTTP de login, cookie, `/me`, logout, revocación y protección del guard, incluyendo health público y configuración de secreto ausente/inválida.
