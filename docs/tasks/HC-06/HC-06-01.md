# HC-06-01 — Imágenes de producción y proxy privado

## Identificación

- **Bloque:** HC-06
- **Estado:** en revisión

## Especificación aprobada

### Objetivo

Preparar builds de producción separados para la web Vue/Vite y la API NestJS, conservando el workspace pnpm y los contratos compartidos. Exponer solo la web y enrutar `/api` a la API por la red privada de Railway.

### Alcance

- Dockerfiles multi-stage para web y API con Node 26.13 y pnpm 12.19.
- Build de contratos antes de compilar cada aplicación.
- Servidor estático no privilegiado con fallback de Vue Router, healthcheck web y proxy `/api`.
- API en runtime Node con migraciones y script de bootstrap disponibles.
- Verificación local de imágenes/builds y de assets de producción.

### Exclusiones

- No usar `compose.yaml` de desarrollo como configuración de producción.
- No crear servicios, variables reales, dominios ni despliegues Railway.
- No ejecutar migraciones de producción ni cambiar el modelo de datos.
- No publicar el API ni PostgreSQL en la red pública.

### Dependencias

- Workspace y lockfile pnpm existentes.
- Servicio API con `PORT`, `/api/health`, cookies seguras y configuración explícita de proxies.
- HC-06-02 para los valores y operaciones de primera publicación.

### Archivos o módulos afectados

- `apps/api/Dockerfile`, `apps/api/package.json`.
- `apps/web/Dockerfile`, `apps/web/deploy/default.conf.template`.
- Pruebas/configuración de build y documentación de HC-06.

### Criterios de aceptación

- Ambas imágenes compilan con contexto raíz y lockfile congelado.
- Runtime API contiene `dist`, dependencias de producción y script administrativo, sin necesitar el checkout.
- Web sirve assets, devuelve fallback SPA y pasa `/healthz`.
- `/api` conserva la ruta `/api/...` al proxy y usa el host privado y puerto del servicio API.
- El proceso web no corre como root; la API no se ejecuta como root.
- No hay migración automática al arrancar.

### Pruebas previstas

- `docker build -f apps/api/Dockerfile` y `docker build -f apps/web/Dockerfile` desde la raíz.
- `pnpm check`, `pnpm architecture:check` y pruebas relevantes.
- Smoke local de `/healthz`, fallback SPA y proxy con servicios aislados, sin base productiva.
- `git diff --check`.

## Ejecución y resultados

### Resumen de implementación

Se añadieron Dockerfiles multi-stage: API Node 26.13 con pnpm 12.19 y despliegue portable de dependencias, y web Vite servida por `nginx/nginx-unprivileged:1.31.10-alpine` fijada por tag y digest. Se sustituyó la imagen 1.27 obsoleta por una imagen oficial actualizada. Nginx resuelve `PORT`/`API_UPSTREAM` al arrancar, conserva rutas `/api`, y aplica fallback SPA. No hay migraciones en el entrypoint.

### Archivos realmente modificados

`apps/api/Dockerfile`, `apps/api/package.json`, `apps/web/Dockerfile`, `apps/web/deploy/default.conf.template`, esta ficha, el índice HC-06, el runbook Railway, `docs/README.md`, `docs/tasks/README.md` y `docs/progress.md`.

### Pruebas ejecutadas y resultados

Superado en la rama actualizada a `main`: se reconstruyeron ambas imágenes con `docker build` desde el contexto raíz. La API contiene `dist`, TypeORM y `scripts/auth-admin.mjs`; arrancó como usuario `node`, conectó a un PostgreSQL 17 temporal aislado sin migraciones y `/api/health` devolvió 200. La web arrancó como UID 101 con `PORT=18080`, `/healthz` devolvió 200, `/api/health` llegó a la API y una ruta profunda devolvió el shell `index.html`. Nginx `1.31.10-alpine` pasó build y smoke con el digest fijado. Se retiraron los contenedores y la red efímeros; los servicios Compose TRAKIA no se modificaron.

La fixture `domain-no-http` quedó resuelta al sincronizar con `main`: el commit HC-05-10-03b cambió `scripts/architecture-check.mjs` y `scripts/architecture-rule-tests.mjs` de lanzar el CLI Dependency Cruiser como proceso hijo a utilizar su API oficial dentro del proceso. La regla `.dependency-cruiser.cjs` no se relajó ni exceptuó y la fixture vuelve a verificar rechazo de HTTP desde `domain/`.

`pnpm architecture:check` independiente pasó (fixtures, dependencia y encapsulación; 242 módulos). `pnpm check` pasó, incluidos lint, formato, tipos, pruebas y builds. `git diff --check` pasó al cierre. El build web mantiene el aviso de Vite por el bundle principal superior a 500 kB.

### Comprobaciones de producción confirmadas después de la primera publicación

El propietario autorizó una fase de pruebas sin backups y confirmó la inicialización operativa. La consulta de solo lectura a Railway del 2026-11-24 muestra web, API y PostgreSQL en línea en `production`; el dominio HTTPS activo es `https://trakia.up.railway.app`. En esa fecha, `/healthz` y `/api/health` a través del proxy público respondieron HTTP 200; API devolvió `{"status":"ok"}`. La API permanece privada. Las migraciones, base y bootstrap se registran en HC-06-02.

### Desviaciones justificadas

Se limitó el paquete API desplegado a `dist` y el script administrativo; `API_UPSTREAM` se configura por referencia Railway para resolver el DNS privado por entorno. El smoke usó PostgreSQL 17 temporal aislado; no ejecutó migraciones.

### Incidencias y riesgos pendientes

El plan indicado para Railway es Limited Trial, con red saliente restringida y límites de recursos/servicios propios del trial; comprobar el plan y sus límites antes de ampliar el uso. No se han configurado backups/PITR por autorización temporal del propietario; esa protección sigue pendiente. El healthcheck API confirma proceso/ruta, no readiness continua de DB. El cambio de resolución DNS dinámica de HC-06-04 se audita y verifica por separado.

### Revisión arquitectónica

- **Resultado:** sin hallazgos arquitectónicos bloqueantes; comprobación independiente satisfactoria tras actualizar `main`.
- **Hallazgos y resolución:** los Dockerfiles mantienen el workspace como contexto y el servidor estático como capa de entrega; `/api` solo usa el nombre privado del servicio. No se añadieron dependencias entre módulos ni cambios de persistencia. Revisadas ADR-015 y `module-conventions.md`; `pnpm architecture:check` pasa con 242 módulos. El fallo anterior procedía del verificador de fixtures basado en CLI/subproceso; se resolvió en `main` mediante la API de Dependency Cruiser, conservando la regla `domain-no-http`.

### Revisión y aceptación

- **Resultado:** en revisión; pendiente de integración en `main` y configuración/smoke de staging por el propietario.
- **Evidencia de revisión y aprobación:** builds, smoke aislado, `pnpm check` y auditoría independiente registrados; no se desplegó ni se accedió a Railway.
