# HC-06-02 — Configuración segura y operaciones iniciales

## Identificación

- **Bloque:** HC-06
- **Estado:** en revisión

## Especificación aprobada

### Objetivo

Documentar la configuración exacta para web, API y PostgreSQL en Railway y un procedimiento controlado de backups, migraciones, bootstrap inicial, comprobación y rollback.

### Alcance

- Documentar referencias de variables, dominios, puertos, healthchecks y privacidad de servicios.
- Mantener API y PostgreSQL privados; web es el único servicio público y `/api` comparte origen HTTPS.
- Ejecutar migraciones manualmente tras comprobar la base efectiva y tener copia recuperable.
- Inicializar el primer usuario con el CLI seguro existente.
- Documentar límites de backups, logging, reinicios y coste sin inventar un importe mensual sin tamaño/uso.

### Exclusiones

- No usar ni escribir credenciales reales.
- No desplegar, conectar a Railway, crear dominios o aplicar migraciones reales.
- No activar `synchronize`, `dropSchema` ni migración automática al arrancar.
- No exponer API, PostgreSQL ni credenciales al cliente web.

### Dependencias

- HC-06-01 para imágenes y puertos.
- Documentación y CLI oficial de Railway; TypeORM y comandos existentes.

### Archivos o módulos afectados

- `docs/deploy/railway.md`.
- Ficha, índice HC-06, `docs/README.md` y `docs/progress.md`.
- API runtime config solo si la auditoría demuestra una incompatibilidad concreta.

### Criterios de aceptación

- Están especificadas `NODE_ENV`, `PORT`, `DATABASE_URL`, `DATABASE_SSL`, `JWT_SECRET`, `CORS_ORIGINS` y `TRUSTED_PROXIES` con sus fuentes y valores esperados.
- DB usa PostgreSQL 17, red privada, volumen y backups/PITR habilitados antes de producción.
- Cookie de sesión Secure/HttpOnly/SameSite, CSRF y CORS se validan bajo el dominio HTTPS único.
- El runbook permite comprobar `current_database()`, mostrar migraciones pendientes y ejecutar el comando explícito solo tras la verificación y backup.
- Bootstrap inicial no imprime credenciales, no acepta usuarios posteriores y requiere terminal segura.
- Costes y disponibilidad se marcan como dependientes del plan, límites y consumo.

### Pruebas previstas

- `pnpm check`, `pnpm architecture:check` si cambia código y `git diff --check`.
- Validación de enlaces/documentación; sin acceso a una cuenta Railway.

## Ejecución y resultados

### Resumen de implementación

Se documentó la topología, las variables Railway concretas, cookies/CSRF, PostgreSQL 17 con volumen persistente, la decisión de TLS de la conexión privada, healthchecks, migración/bootstrap controlados, backups, límites de coste y smoke de publicación. La web no es instalable como PWA hoy; la implementación queda fuera del alcance de esta fase en HC-06-03.

### Archivos realmente modificados

`docs/deploy/railway.md`, ficha, índice HC-06, índice documental y progreso.

### Pruebas ejecutadas y resultados

Superado: contraste del runbook con la configuración API/web y documentación oficial Railway y del template Postgres. La decisión `DATABASE_SSL=false` es compatible con WireGuard y el acceso privado, con la limitación explícita de que no se autentica TLS del servidor PostgreSQL. `pnpm architecture:check` independiente pasó con 242 módulos; `pnpm check` y `git diff --check` pasaron. Sin credenciales reales, conexión a Railway, migraciones ni despliegue.

### Desviaciones justificadas

La imagen Railway `postgres-ssl` crea una CA/certificado autofirmado y TypeORM exige un certificado confiable cuando `DATABASE_SSL=true`; la configuración actual no inyecta esa CA. Por ello se propone `DATABASE_SSL=false` solo en el segmento privado cifrado WireGuard, sin afirmar autenticación TLS del servidor. Si se requiere TLS autenticado, hay que añadir soporte de CA/hostname y validarlo en staging antes de producción.

### Incidencias y riesgos pendientes

Permanecen pendientes backup/PITR real, dominio final, comprobar en Railway que `DATABASE_URL` usa DNS privado y `current_database()` coincide, aplicar migraciones tras el backup, bootstrap, PWA y smoke de producción. No se ejecutaron conexiones ni operaciones Railway desde Codex.

### Revisión arquitectónica

- **Resultado:** sin impacto arquitectónico por alcance documental.
- **Hallazgos y resolución:** no altera contratos, persistencia ni servicios; alcance documental sin impacto arquitectónico. La verificación independiente pasó tras integrar en `main` la corrección del runner. No se alteraron reglas arquitectónicas.

### Revisión y aceptación

- **Resultado:** en revisión; pendiente de integración en `main` y configuración/operación por el propietario.
- **Evidencia de revisión y aprobación:** runbook contrastado con código y fuentes oficiales actuales; sin credenciales ni servicios reales.
