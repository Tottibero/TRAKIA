# HC-06-02 — Configuración segura y operaciones iniciales

## Identificación

- **Bloque:** HC-06
- **Estado:** en revisión

## Especificación aprobada

### Objetivo

Documentar la configuración exacta para web, API y PostgreSQL en Railway y un procedimiento controlado de backups, migraciones, bootstrap inicial, comprobación y rollback.

### Alcance

- Documentar referencias de variables, dominios, puertos, healthchecks y privacidad de servicios.
- Mantener API y PostgreSQL privados; web es el único servicio público y `/api` comparte origen HTTPS.
- Ejecutar migraciones manualmente tras comprobar la base efectiva y tener copia recuperable.
- Inicializar el primer usuario con el CLI seguro existente.
- Documentar límites de backups, logging, reinicios y coste sin inventar un importe mensual sin tamaño/uso.

### Exclusiones

- No usar ni escribir credenciales reales.
- No desplegar, conectar a Railway, crear dominios o aplicar migraciones reales.
- No activar `synchronize`, `dropSchema` ni migración automática al arrancar.
- No exponer API, PostgreSQL ni credenciales al cliente web.

### Dependencias

- HC-06-01 para imágenes y puertos.
- Documentación y CLI oficial de Railway; TypeORM y comandos existentes.

### Archivos o módulos afectados

- `docs/deploy/railway.md`.
- Ficha, índice HC-06, `docs/README.md` y `docs/progress.md`.
- API runtime config solo si la auditoría demuestra una incompatibilidad concreta.

### Criterios de aceptación

- Están especificadas `NODE_ENV`, `PORT`, `DATABASE_URL`, `DATABASE_SSL`, `JWT_SECRET`, `CORS_ORIGINS` y `TRUSTED_PROXIES` con sus fuentes y valores esperados.
- DB usa PostgreSQL 17, red privada, volumen y backups/PITR habilitados antes de producción.
- Cookie de sesión Secure/HttpOnly/SameSite, CSRF y CORS se validan bajo el dominio HTTPS único.
- El runbook permite comprobar `current_database()`, mostrar migraciones pendientes y ejecutar el comando explícito solo tras la verificación y backup.
- Bootstrap inicial no imprime credenciales, no acepta usuarios posteriores y requiere terminal segura.
- Costes y disponibilidad se marcan como dependientes del plan, límites y consumo.

### Pruebas previstas

- Revisión del runbook contra la configuración efectiva del código y docs oficiales Railway.
- `pnpm check`, `pnpm architecture:check` si cambia código y `git diff --check`.
- Validación de enlaces/documentación; sin acceso a una cuenta Railway.

## Ejecución y resultados

### Resumen de implementación

Se documentó la topología, las variables Railway concretas, cookies/CSRF, PostgreSQL 17 con volumen persistente, la decisión de TLS de la conexión privada, healthchecks, migración/bootstrap controlados, backups, límites de coste y smoke de publicación. La verificación posterior confirmó producción en Railway y se conserva como resultado de operación, no como parte de la preparación local original.

### Archivos realmente modificados

`docs/deploy/railway.md`, ficha, índice HC-06, índice documental y progreso.

### Pruebas ejecutadas y resultados

Superado en la preparación local: contraste del runbook con la configuración API/web y documentación oficial Railway y del template Postgres. La decisión `DATABASE_SSL=false` es compatible con WireGuard y el acceso privado, con la limitación explícita de que no se autentica TLS del servidor PostgreSQL. `pnpm architecture:check` independiente pasó con 242 módulos; `pnpm check` y `git diff --check` pasaron.

### Comprobaciones de producción confirmadas por el propietario y Railway CLI

- El 2026-11-24 Railway mostró los tres servicios `web`, `api` y `postgres` en línea, en `production`; `web` expone `https://trakia.up.railway.app`, y API/PostgreSQL no tienen dominio público.
- `SELECT current_database()` mediante el DataSource compilado devolvió `trakia`.
- Las 17 migraciones desplegadas se mostraron pendientes, coincidieron con el código esperado y se ejecutaron una vez. La comprobación posterior mostró las 17 aplicadas y ninguna pendiente.
- El propietario ejecutó interactivamente `node scripts/auth-admin.mjs bootstrap`. La verificación posterior contó un registro en `users`, sin leer ni mostrar el correo.
- `/healthz` y `/api/health` por el dominio público respondieron HTTP 200; el endpoint API devolvió `{"status":"ok"}`. Railway informó el servicio web/API/PostgreSQL en línea.
- No se configuraron backups/PITR por decisión temporal expresa del propietario para esta fase de pruebas.
- El proyecto está en Railway Limited Trial según el contexto del propietario. Railway documenta restricciones de red saliente y puertos disponibles, límites de trial (1 GB de memoria por servicio, CPU compartida y hasta cinco servicios por proyecto) y retención de volúmenes limitada tras finalizar los créditos. Estos límites no son una medición de consumo ni sustituyen la revisión de cuenta/plan. Fuente: [Railway Free Trial](https://docs.railway.com/pricing/free-trial).

### Desviaciones justificadas

La imagen Railway `postgres-ssl` crea una CA/certificado autofirmado y TypeORM exige un certificado confiable cuando `DATABASE_SSL=true`; la configuración actual no inyecta esa CA. Por ello se propone `DATABASE_SSL=false` solo en el segmento privado cifrado WireGuard, sin afirmar autenticación TLS del servidor. Si se requiere TLS autenticado, hay que añadir soporte de CA/hostname y validarlo en staging antes de producción. La operación real de migraciones se autorizó para la fase de pruebas aunque no hubiera una copia de backup; la exigencia de crear/verificar backups antes de aceptar uso de producción sigue pendiente.

### Incidencias y riesgos pendientes

No hay backups/PITR configurados por la excepción temporal autorizada. La limitación y retención asociadas a Railway Limited Trial requieren vigilar créditos, uso y continuidad del volumen; los límites exactos de la cuenta no se consultaron en la facturación. La verificación de cookies/sesión autenticada y escrituras CSRF no forma parte de los healthchecks y no se declara realizada aquí. La instalación manual Android/iOS corresponde al propietario en HC-06-03.
