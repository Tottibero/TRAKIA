# HC-06-04 — Resolución dinámica del upstream privado

## Identificación

- **Bloque:** HC-06
- **Estado:** en revisión

## Especificación aprobada

### Objetivo

Evitar que Nginx conserve una IP privada obsoleta de la API después de un redespliegue de Railway.

### Alcance

- Resolver el hostname privado de API en tiempo de ejecución mediante el resolver DNS que Railway entrega al contenedor web.
- Configurar Nginx para volver a resolver el upstream tras expirar su caché, sin reiniciar la web.
- Mantener el proxy `/api`, el puerto `$PORT`, el nombre/puerto de `API_UPSTREAM`, los encabezados de seguridad y el origen único.
- Añadir un smoke reproducible que cambie el destino DNS mientras Nginx sigue en ejecución.
- Documentar la decisión, el comportamiento y sus límites.

### Exclusiones

- No modificar API, contratos, persistencia ni reglas deportivas.
- No fijar direcciones DNS de Docker Compose ni direcciones IP privadas de Railway.
- No cambiar variables, dominios, imágenes o servicios del proyecto Railway.
- No desplegar esta corrección desde la tarea.

### Dependencias

- HC-06-01: imagen de producción Nginx unprivileged y proxy `/api`.
- HC-06-02: referencia `API_UPSTREAM` al dominio privado y puerto de API.
- Imagen actual fijada `nginx/nginx-unprivileged:1.31.10-alpine`.

### Archivos o módulos afectados

- `apps/web/Dockerfile`.
- `apps/web/deploy/default.conf.template`.
- Smoke de integración del proxy en `apps/web/scripts/`.
- `apps/web/package.json` si se añade un comando de ejecución.
- `docs/deploy/railway.md`, esta ficha, índice HC-06 y `docs/progress.md`.

### Criterios de aceptación

- Nginx obtiene sus resolvers de la configuración DNS efectiva del contenedor en runtime; no usa la dirección de Docker Compose como supuesto de Railway.
- `/api/...` pasa por `API_UPSTREAM` con la ruta, query y encabezados existentes.
- Al cambiar la IP que resuelve el dominio privado, Nginx alcanza el nuevo upstream dentro del TTL configurado sin reiniciarse.
- Se conservan `/healthz`, `$PORT`, cookies, CSRF, `Host`, `X-Real-IP`, `X-Forwarded-For` y `X-Forwarded-Proto`.
- El API y las reglas deportivas no cambian.

### Pruebas previstas

- Build Docker de producción web y API.
- Smoke con dos upstreams sucesivos bajo el mismo hostname; verificar que la misma instancia Nginx alcanza al segundo y conserva URI/query y encabezado CSRF.
- `pnpm check`, `pnpm architecture:check`, pruebas web relevantes y `git diff --check`.

## Ejecución y resultados

### Resumen de implementación

Nginx habilita el resolver local que la imagen oficial obtiene desde `/etc/resolv.conf` y usa `proxy_pass` con una variable para resolver de nuevo el hostname privado. La caché DNS se limita a 10 segundos. El smoke local sustituyó un upstream por otro con el mismo alias mientras Nginx seguía activo; el segundo destino recibió la ruta y query esperadas.

### Archivos realmente modificados

`apps/web/Dockerfile`, `apps/web/deploy/default.conf.template`, `apps/web/package.json`, `apps/web/scripts/smoke-dynamic-proxy.mjs`, `docs/deploy/railway.md`, esta ficha, el índice HC-06 y `docs/progress.md`.

### Pruebas ejecutadas y resultados

Superado: `pnpm check` (lint, formato, tipos, arquitectura con 248 módulos, 104 pruebas API, 188 pruebas web y builds), build Docker de producción web (`trakia-web:hc06-final`) y API (`trakia-api:hc06-final`), smoke de artefactos PWA, smoke Docker del proxy con la imagen web final, `pnpm architecture:check` independiente (248 módulos sin violaciones), `pnpm format:check` y `git diff --check`. El smoke confirmó `/healthz` 200, preservación de URI/query, cookie, Origin, CSRF y encabezados; después reemplazó el upstream DNS y Nginx pasó de `deployment-a` a `deployment-b` sin reiniciarse. La primera ejecución del smoke detectó una carrera del propio harness al consultar `/healthz` antes de que Nginx estuviera listo; se añadió una espera acotada de hasta 30 segundos y la repetición pasó.

### Desviaciones justificadas

No se desplegó la corrección en Railway; el alcance solicitado limita la validación a build y smoke local, sin modificar la configuración ni los servicios alojados.

### Incidencias y riesgos pendientes

Tras un cambio de IP, una petición que use la respuesta DNS aún cacheada durante hasta 10 segundos puede fallar. Nginx no añade health checks activos ni reintenta solicitudes de escritura; el cliente debe tratar cualquier error como resultado no guardado. La validación del cambio tras un redespliegue real en Railway queda para el siguiente despliegue autorizado.

### Revisión arquitectónica

- **Resultado:** sin hallazgos bloqueantes ni recomendaciones. El cambio solo modifica la configuración de Nginx y un smoke de infraestructura web; no introduce dependencias entre módulos, no altera contratos y no toca API, persistencia ni dominio.
- **Reglas revisadas:** ARCH-WEB-003 (el proxy permanece en la capa de infraestructura web y no crea clientes propios en features), ARCH-ALL-001 y ARCH-ALL-002 (sin nuevos ciclos ni dependencias entre workspaces). La tarea no afecta las reglas de límites de módulos backend.
- **Evidencia:** revisión del diff de `apps/web/Dockerfile`, `apps/web/deploy/default.conf.template` y `apps/web/scripts/smoke-dynamic-proxy.mjs`, junto con ADR-015 y `module-conventions.md`; `pnpm architecture:check` pasó con 248 módulos y sin violaciones.
