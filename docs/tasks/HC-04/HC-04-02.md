# HC-04-02 — Contratos y API de consulta semanal y detalle

## Identificación

- **Bloque:** HC-04 — Home semanal y detalle de entrenamiento
- **Estado:** completada

## Especificación aprobada

### Objetivo

Publicar contratos Zod y endpoints autenticados de solo lectura para consultar siete fechas civiles de planificación conjunta y el detalle de una sesión, respetando el diseño aprobado en [HC-04-01](HC-04-01.md).

### Alcance

- Contratos estrictos de calendario, resumen de bloques, referencias descriptivas de ejercicios y detalle completo de sesión.
- `GET /api/training-plans/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`, limitado a lunes-domingo consecutivos, con todos los planes, sesiones y descansos explícitos, además de `hasImportedPlans`.
- `GET /api/training-plans/:planId/sessions/:sessionId`, identificado por UUID interno y con comprobación de pertenencia.
- Lecturas SQL acotadas y proyecciones propias de `training-plans`, sin entidades TypeORM en respuestas ni escrituras.
- Resolución de ejercicios mediante una consulta agrupada pública de `ExerciseCatalogService`; conservar la identidad interna y representar claves descriptivas ausentes o ambiguas sin inventarlas.
- Pruebas de contratos, servicio, HTTP/seguridad e integración PostgreSQL aislada; documentación de resultados, auditoría y dependencias posteriores.

### Exclusiones

No cambiar JSON v1, migraciones ni datos persistidos; no añadir UI Vue, estados o acciones de ejecución, persistencia offline, paginación semanal, importación, edición, ni cambios a HC-02/HC-03. No gestionar Docker, publicar ramas, abrir PR ni hacer merge. El commit local de cierre requiere autorización expresa del propietario; HC-04-03 no se inicia en esta tarea.

- Autenticación global actual, ADR-014, ADR-015 y convenciones modulares.

### Criterios de aceptación

1. El calendario valida fechas civiles reales y exactamente siete días de lunes a domingo; devuelve siete fechas, entradas de todos los planes, descansos explícitos, sesiones múltiples y `hasImportedPlans`.
2. Las entradas tienen orden total, determinista y neutral; la consulta no pagina ni crea o modifica datos.
3. Las fechas PostgreSQL `date` se serializan como `YYYY-MM-DD`, sin conversión horaria.
4. El detalle verifica UUID y pertenencia de la sesión, responde 404 para recursos o asociaciones incorrectas y carga solo esa sesión.
5. Los DTO conservan orden, modalidades `sets`/`circuit`/`intervals`, rondas/AMRAP, fases, descansos, objetivos, ajustes y alternativas; no exponen entidades ni modifican JSON v1.
6. La consulta agrupada pública de ejercicios deduplica UUID; representa identidad interna, nombre no disponible y referencias de catálogo ambiguas sin selección arbitraria ni claves sintéticas.
7. Ambos endpoints quedan tras autenticación global; entrada inválida devuelve 400, falta de autenticación 401 y errores inesperados no revelan detalles internos.
8. No se consultan tablas privadas de otro módulo, no hay consultas N+1, no se generan escrituras y no se muestran estados ficticios de ejecución.
9. Contracts, verificaciones locales, pruebas HTTP e integración PostgreSQL en `trakia_test` pasan; la auditoría arquitectónica independiente queda registrada y sin hallazgos bloqueantes.
10. Antes de la revisión del propietario, HC-04-02 queda `en revisión`; HC-04-03 a HC-04-06 permanecen como planificación.

## Ejecución y resultados

### Resumen de implementación

Se añadieron dos consultas autenticadas de solo lectura: el calendario semanal valida un lunes y su domingo consecutivo, devuelve siete fechas y distingue `hasImportedPlans`; el detalle identifica plan y sesión por UUID y comprueba su pertenencia. Ambas consultas usan una transacción PostgreSQL `REPEATABLE READ READ ONLY`.

Los contratos Zod estrictos proyectan resúmenes de bloques para la Home y el detalle completo para `sets`, circuitos fijos, AMRAP e intervalos. Se conservan objetivos originales, ajustes por serie/ronda, descansos, alternativas y fases. `ExerciseCatalogService.findSummariesByIds` resuelve UUIDs agrupados y deduplicados; el contrato devuelve todas las claves catalogadas, la clave histórica almacenada si existe y un estado explícito `stored`, `unique`, `ambiguous` o `unavailable`. Nunca sintetiza claves. No se cambió JSON v1 ni se consultó `workouts`.

### Desviaciones justificadas

La primera ejecución del runner se invocó con una URL de `trakia_test` sin usuario ni contraseña y fallaron los escenarios existentes de autenticación. Se reconstruyó la URL en memoria desde las variables locales, sin mostrar valores ni cambiar archivos, y el runner verificó el destino autorizado antes de migrar; la ejecución final terminó en 0. Una aserción unitaria inicial tampoco contabilizaba `SET TRANSACTION READ ONLY`; se corrigió para incluir la consulta de control y `pnpm check` final pasó.

### Incidencias y riesgos pendientes

- `workouts` aún no expone una capability pública de estados reales; HC-04 no muestra estados y HC-05 deberá resolver esa dependencia antes de hacerlo.
- La restricción global de unicidad existente para `planKey` permanece intacta; la API usa UUID en las rutas y conserva `(origin, planKey)` en datos de dominio.
- Para referencias históricas sin clave persistida y con varias claves de catálogo, el DTO conserva UUID y nombre si existe, devuelve todas las claves y marca `ambiguous`; sin nombre muestra `null`/`unavailable`. No elige una clave ni crea `unresolved-*`.
- HC-04-03 y HC-04-04 pueden consumir los contratos publicados; HC-04-05 y HC-04-06 siguen pendientes y no se han iniciado.
