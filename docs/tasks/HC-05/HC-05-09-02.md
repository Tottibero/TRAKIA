# HC-05-09-02 — Simplificación del modelo de ejecución online

## Identificación

- **Bloque:** HC-05
- **Estado:** completada
- **Tipo:** especificación técnica y documentación; no implementa código ni persiste cambios deportivos.

## Objetivo

Definir el modelo mínimo de ejecución siempre online, con PostgreSQL como fuente de verdad y NestJS como autoridad de las transiciones deportivas. Vue mantiene únicamente presentación temporal. Esta especificación sustituye las decisiones local-first de ejecución de HC-05 sin reescribir sus fichas históricas.

## Decisión objetivo y decisiones sustituidas

1. PostgreSQL conserva la única versión autoritativa de cada ejecución, sus resultados, pausas, tiempos, cierre y correcciones.
2. NestJS valida snapshot, pertenencia de unidades, transiciones y reglas deportivas; responde con el estado confirmado. Vue solo deriva presentación y captura formularios volátiles.
3. Iniciar, registrar, pausar, reanudar, avanzar, cerrar y corregir requiere conexión y respuesta aceptada. Ante error o incertidumbre la UI conserva el estado confirmado, presenta el error y consulta/reintenta la operación aplicable; no avanza de forma optimista.
4. Puede existir como máximo una ejecución `in_progress` o `paused` por usuario. No existe propiedad de dispositivo ni transferencia entre dispositivos.
5. Se elimina IndexedDB de ejecuciones, resultados y borradores persistentes; no hay cola offline ni reconciliación diferida.
6. Idempotencia se limita a duplicados HTTP posibles: `requestId` de inicio, ID del resultado, ID de corrección y transiciones con una identidad/precondición de dominio estable. No se adopta secuencia global de operaciones, ledger genérico ni revisión/versionado sin caso concreto.
7. Los temporizadores se reconstruyen desde timestamps confirmados y la hora actual, descontando pausas persistidas. Vue puede tener un intervalo volátil para repintar la cuenta atrás, nunca como fuente de tiempo.

## Modelo mínimo de datos

Una fila de `workout_executions`, propiedad de `workouts`, representa la ejecución completa. Columnas escalares e índices no duplican el documento externo: son una representación de persistencia del mismo agregado.

| Dato persistente | Contenido y motivo |
| --- | --- |
| Identidad y propiedad | `id`, `user_id`, `plan_id`, `session_id`; claves estables `planKey`/`sessionKey` y snapshot para conservar la planificación original. `request_id` solo como clave del inicio HTTP y con unicidad por usuario. Sin `device_id`. Filas históricas anteriores al inicio por usuario pueden conservar `user_id`/snapshot nulos; no hacer esos campos obligatorios ni borrar filas sin un plan de backfill justificado. |
| Estado temporal deportivo | `status`, `started_at`, `finished_at`, `pauses[]` con inicio/fin. Una pausa abierta equivale a `paused`; no guardar duración agregada, que se deriva de intervalos. |
| Snapshot | Sesión planificada y catálogo/alternativas/métricas necesarios para interpretar resultados históricos, conforme a `WorkoutExecutionSnapshotSchema`. |
| Resultados actuales | `results[]` con ID, bloque, aparición/unidad, ejercicio realmente usado, estado y métricas reales. El orden de inserción confirmado por la transacción conserva el orden de registro; unidad/posición se derivan. No se añade timestamp por resultado: para temporizadores no derivables existe un único ancla activa. Se conserva cada serie, repetición, peso, duración, distancia, RPE y calorías cuando fueron registradas. |
| Temporizador no derivable | Como máximo un `active_timer` mientras haya una ventana activa cuyo ancla no se derive. Descanso: `{kind, blockKey, resultId, startedAt}`. AMRAP: `{kind, blockKey, startedAt}`. HIIT: `{kind, blockKey, cycleIndex, phaseKey, startedAt}`. `startedAt` lo asigna el servidor; duración se obtiene del snapshot. No guardar segundos restantes, ticks ni cursor general. Al avanzar, reemplazar/limpiar en la misma transacción. |
| Cierre | `finished_at` y datos finales existentes (`feeling`, `observations`, `completionType`, `closureReason`). No almacenar cierre pendiente, sobre de reconciliación ni copia de resultados enviada por el cliente. |
| Correcciones | Valor vigente en `results[]` e historial inmutable de correcciones con IDs estables, `before`/`after` y fecha. Se conserva auditoría; la identidad de corrección sirve también para reconocer reintentos. |

El cursor de ejercicio/serie/ronda/fase se calcula desde snapshot y resultados confirmados; la ronda de circuito se deriva de sus resultados. Unidades `not_reached`, cumplimiento, duración activa, resumen, siguiente etiqueta, formulario seleccionado y cuenta atrás visible son proyecciones, no columnas. `active_timer` es la única excepción para ventanas cuyo inicio no se reconstruye de forma fiable de snapshot/resultados.

### Unidades, precisión y valores de las métricas

Se toma como regla canónica la semántica del contrato actual `ActualMetricsSchema`: todo valor presente es numérico y estrictamente mayor que cero. La validación compartida objetivo explicitará además finitud (`finite().positive()`) para rechazar valores no representables por JSON/Number. Se aceptan decimales para todas las métricas, sin redondeo, paso mínimo, máximo ni límite adicional dentro de la precisión JSON/Number. La omisión se expresa dejando la propiedad ausente, nunca con cero o `null`. La misma Zod valida cliente y API; el backend además aplica compatibilidad de métrica con el ejercicio real. Las correcciones usan la misma regla.

| Campo externo | Unidad | Valores admitidos |
| --- | --- | --- |
| `reps` | repeticiones, sin unidad física | Número finito `> 0`; decimales admitidos porque el contrato vigente no restringe a enteros. |
| `weightKg` | kilogramos de carga externa total | Número finito `> 0`; decimales sin paso impuesto. |
| `durationSeconds` | segundos | Número finito `> 0`; decimales admitidos. |
| `distanceMeters` | metros | Número finito `> 0`; decimales admitidos. |
| `rpe` | escala subjetiva sin unidad | Número finito `> 0`; sin máximo porque ni el contrato ni una decisión de dominio fijan escala superior. |
| `calories` | kilocalorías (kcal) | Número finito `> 0`; decimales admitidos por el contrato vigente. |

La UI usa `step="any"` y no fija `min`/`max` nativos que impongan una regla distinta; la validación compartida rechaza cero, negativos, `NaN` e infinitos. Los valores de planificación comparten nombres de métrica y positividad, pero sus objetivos no limitan los resultados reales. Si el producto necesita repeticiones enteras, un rango de RPE u otra granularidad, se requiere decisión de dominio y cambio común a contrato, API, UI y correcciones; no se infiere de controles HTML.

### Marcas temporales mínimas

- **Ejecución:** `startedAt` al reservar, `finishedAt` al cerrar. PostgreSQL asigna ambos.
- **Serie/ejercicio/circuito:** no guardar una fecha por cada resultado. Cuando un resultado confirmado inicia un descanso planificado, la misma transacción persiste el ancla `active_timer.startedAt` y su `resultId`; la duración se lee del snapshot.
- **AMRAP:** al entrar en el bloque, persistir `active_timer` con `kind`, `blockKey` y `startedAt`. La ventana/duración se deriva del snapshot; ronda actual y ronda parcial se derivan de resultados. Expiración = timestamp + ventana menos pausas solapadas. No escribir un evento de timeout ni resultado ficticio.
- **HIIT:** persistir el ancla de fase activa (`blockKey`, `cycleIndex`, `phaseKey`, `startedAt`); la ventana se deriva del snapshot. Un avance confirmado reemplaza el ancla con hora de servidor. Fase de trabajo vencida exige confirmar el resultado real; fase pasiva puede avanzar sin resultado deportivo. No se guardan ticks ni tiempo restante.
- **Pausa:** conservar los intervalos `WorkoutPause` existentes, con `startedAt` y `finishedAt` asignados por API. Temporizador transcurrido = tiempo desde su ancla menos la intersección con pausas. Pausar/reanudar no modifica el ancla ni acumula segundos.

Solo puede haber un `active_timer` por ejecución. No se persisten `elapsedSeconds`, ticks, contador de UI, `finishedAt` de temporizador ni duración duplicada. En descanso tras serie, el ancla empieza al confirmar el resultado, no al pulsar antes de completar sus métricas.

### Semántica deportiva

- Fuerza y circuitos conservan las unidades previstas, adicionales, resultado `performed`/`skipped`, alternativa elegida y métricas compatibles con el ejercicio real. Una omisión explícita no lleva ejercicio ni métricas. NestJS no acepta unidades duplicadas ni resultados ajenos al snapshot.
- Repeticiones, peso en kg, duración en segundos, distancia en metros, RPE y calorías mantienen los nombres y unidades de `ActualMetricsSchema`; los campos ausentes no son cero. La alternativa debe estar permitida por la planificación y sus métricas soportadas.
- AMRAP conserva solo resultados de trabajo realmente confirmados, con ronda contigua y posible ronda final parcial. El vencimiento cierra la ventana; no crea ronda, ejercicio ni resultado ficticio. La ronda/posición se deriva de resultados.
- HIIT conserva las fases/ciclos previstos y resultados reales de trabajo con `activeSeconds` y `windowProgressSeconds` cuando proceda. El descanso pasivo no se convierte en resultado de trabajo. Una fase de trabajo vencida requiere confirmación del trabajo real antes de persistirlo; el paso automático no atribuye trabajo.
- Pausar cierra el cálculo del tiempo activo mediante una marca de servidor y abre `WorkoutPause`; reanudar cierra esa pausa. Temporizadores se congelan durante pausas. Descanso planificado no suma a pausa general.
- **Cambio respecto a D4 de HC-05-08:** no se inicia un descanso antes de que PostgreSQL confirme el resultado de la serie/ronda. Se envían resultado y métricas; la misma transacción crea `active_timer` si corresponde. Vue muestra la cuenta atrás tras la respuesta. El formulario no confirmado es temporal y puede perderse al recargar; retenerlo localmente requeriría persistencia excluida por esta arquitectura.
- El cierre es terminal y atómico. Unidades sin resultado quedan `not_reached` derivadas; no se insertan resultados para ellas. La corrección no cambia identidad, snapshot, planificación ni estado terminal.

## Contratos y API mínimos

Los contratos existentes ya modelan snapshot, estado, pausas, resultados, métricas, cierres y correcciones. Hoy `WorkoutExecutionStartRequest` incluye `requestId` y `deviceId`; `WorkoutExecutionResultRequest` incluye `deviceId`; `WorkoutExecutionOpenResponse` discrimina entre dispositivo actual/ajeno; cierre y corrección usan `WorkoutSyncOperation` con `operationId`, `deviceId` y secuencia. Esos campos/protocolos técnicos no forman parte del modelo deportivo y se eliminan del objetivo.

Los nombres son el destino de diseño; HC-05-09-03 validará rutas finales y esquemas Zod contra el código antes de implementarlos. Reutilizar snapshot, `WorkoutExecutionSchema`, `WorkoutResultSchema`, `WorkoutPauseSchema`, `WorkoutCorrectionSchema` y tipos finales actuales siempre que su semántica coincida. Mantener en respuesta de resultado la confirmación mínima existente (`result`, `replayed`), ampliándola solo para el ancla de temporizador si la escritura la inicia. No devolver/reenviar el agregado completo por cada resultado. Retirar los sobres de `workout-sync` destinados al cierre local/reconciliación; no retirar la entidad deportiva `WorkoutCorrection`.

| Operación | Endpoint y entrada | Validación/escritura/respuesta; duplicados y recuperación |
| --- | --- | --- |
| Iniciar | `POST /workouts/executions/start`; `requestId`, `planId`, `sessionId`. | Zod estricto; sesión y snapshot resueltos por capacidades públicas, locks HC-03 compartidos con importación, índice único parcial por usuario. Guardar ejecución `in_progress`; devolver agregado confirmado. Mismo `requestId` y contenido reproduce respuesta; contenido distinto es conflicto. Si otra ejecución ya está abierta, responder conflicto y no reemplazarla. |
| Recuperar | `GET /workouts/executions/open`; sin `deviceId`. | Endpoint principal tras recarga: autenticar usuario y devolver `none` o la ejecución abierta completa, incluidas pausas/resultados/`active_timer`. No añadir `GET /:id` en HC-05-09; vista cerrada fuera de alcance por ahora. Reconsiderarlo solo si una necesidad concreta no se resuelve con las consultas de historial existentes. |
| Registrar serie/ejercicio/resultado | `POST /workouts/executions/:id/results`; un `WorkoutResult` con ID estable. | Zod + validación de snapshot, alternativa/métricas, estado abierto, unidad/cursor derivado y omisión permitida. Transacción con lock de fila: insertar resultado y, cuando proceda, iniciar/reemplazar el ancla de descanso. Responder el resultado confirmado con forma mínima `{result, replayed}` más ancla solo si se creó. Mismo ID y contenido es replay; mismo ID distinto contenido o unidad duplicada es conflicto. Los IDs actuales permiten idempotencia sin tabla de operaciones. |
| Omitir | Mismo endpoint de resultados, `status: skipped`. | Misma validación estructural que `performed`, sin `actualExerciseKey` ni métricas; aceptar series, ejercicios de circuito e intervalos según unidad del snapshot. La omisión confirmada se conserva como resultado y hace derivable el siguiente paso. |
| Temporizadores (paso posterior) | `POST /workouts/executions/:id/timers`; comandos acotados (`start_window`, `advance_expired`, `finish_early` donde se permita). No forma parte de HC-05-09-03. | Bajo lock, validar temporizador/transición contra snapshot/resultados; timestamp del servidor. `active_timer` identifica fase/ancla necesaria. La respuesta confirma ancla o expiración. Precondición de ancla y claves evita doble avance; el servidor comprueba expiración descontando pausas. Nunca crea resultado por vencimiento. |
| Pausar | `POST /workouts/executions/:id/pause`; sin tiempo del cliente. | Solo `in_progress`; guardar pausa abierta y `paused` en transacción, hora de servidor. Repetición en `paused` devuelve el mismo estado sin añadir otra pausa. Estado confirmado es la respuesta para la UI. |
| Reanudar | `POST /workouts/executions/:id/resume`; identifica `startedAt` de la pausa abierta esperada. | Solo la pausa vigente; cerrarla y cambiar a `in_progress` atómicamente. El timestamp precondicional hace seguro el replay y rechaza una petición vieja si existe una pausa posterior. Devuelve estado confirmado. |
| Cerrar | `POST /workouts/executions/:id/close`; metadatos finales actuales. | Transacción verifica propiedad, ejecución abierta y metadatos; `finished_at` del servidor, cierra una pausa abierta al mismo instante si se permite cierre estando pausado, guarda terminalmente. No acepta copia completa de resultados. Repetición devuelve la ejecución cerrada; cierre contradictorio es conflicto. La validación estructural no debe rechazar unidades pendientes: quedan `not_reached` derivadas. |
| Corregir | `POST /workouts/executions/:id/corrections`; `WorkoutCorrection` con ID, resultado, cambios `before`/`after` y fecha de corrección servidor. | Solo ejecución cerrada; lock de fila, comprobar resultado vigente/snapshot/alternativa/métricas, actualizar valor y añadir historia en transacción. Repetición del mismo ID/contenido reproduce éxito; identidad contradictoria o `before` obsoleto es conflicto. Sin dispositivo ni secuencia de operación. |

Para toda operación, un error de validación no cambia PostgreSQL ni la vista confirmada. Una respuesta perdida se resuelve consultando `GET /workouts/executions/open` y repitiendo solo con la identidad estable ya existente; no se genera una cola. Las operaciones simples de estado usan transición idempotente o precondición deportiva, sin nueva columna de revisión.

## Datos heredados de IndexedDB

Antes de retirar lecturas/escrituras antiguas, la primera versión online comprobará en modo lectura si existe `trakia-workout-execution` y clasificará sus claves/ejecuciones. Se cotejan por `executionId`, ID de resultado y contenido con los datos del servidor. Si queda un inicio ambiguo, se consulta la operación de inicio existente; no se interpreta `deviceId` como propietario. Si hay ejecución o resultado local no presente en PostgreSQL, se bloquea la eliminación y se presenta para revisión/exportación. El usuario podrá reintroducir los datos revisados por las operaciones normales online; no hay carga en segundo plano, importador automático ni cola. La base local se conserva hasta que el usuario confirme la revisión y la aplicación tenga evidencia de que no quedan resultados exclusivos locales. La retirada del store va en otra tarea después de validar el flujo online. Ninguna migración o actualización borra datos.

## Incoherencias que resuelve la implementación

- Omisión: `WorkoutResultSchema` permite `skipped` para fuerza/circuito, pero `recordResult()` del backend lo rechaza salvo en intervalos. HC-05-09-03 debe alinear contratos, backend y UI para la misma política de omisión.
- Métricas: el contrato aplica positividad y la UI añade mínimos/pasos que API no valida. Esta ficha resuelve la divergencia manteniendo positividad, haciendo finitud explícita y usando precisión decimal libre; el formulario no impondrá rangos ni pasos adicionales.
- Recuperación y todas las operaciones: hoy usan `deviceId`; se sustituye por usuario autenticado.
- Estado y temporizadores: pausas, cursor y temporizadores no se persisten en servidor durante la ejecución; la propuesta guarda solo estado deportivo y anclas no derivables.
- Cierre: hoy consolida resultados locales al cerrar; se elimina la fusión de datos no confirmados.
- Avance: el frontend actualmente calcula siguiente unidad; NestJS validará y devolverá estado confirmado antes de que Vue avance.
- Resultados y correcciones: preservar validación de snapshot, alternativos, métricas, duplicados, AMRAP parcial e historial `before`/`after` mientras desaparece el protocolo genérico de sincronización.

## Dependencias y propuesta para HC-05-09-03

HC-05-09-03 debe ser el primer corte vertical implementable, tras completar la revisión/aceptación de HC-05-08. Depende de contratos HC-02-04, locks de sesión HC-03-05/06, capacidades públicas de `training-plans`/`exercises`, auth HTTP y persistencia `workouts` existentes.

Una unidad prevista, métricas del contrato actual y validación de snapshot; el backend confirma antes de que Vue avance. Tests de contrato (incluidos ceros/negativos rechazados, decimales admitidos e infinitos rechazados), servicio/API e integración en `trakia_test` para índice por usuario, atomicidad, snapshot, repetición/conflicto, persistencia y recuperación `open`. Pasos posteriores verificables: HC-05-09-04 pausas/reanudación, con tests de transiciones, pausa abierta y reconstrucción temporal tras recarga, más prueba manual pausar-recargar-reanudar; HC-05-09-05 descansos y temporizadores AMRAP/HIIT, con reloj controlado, duración derivada, pausas descontadas y pruebas de no crear resultados por timeout, más prueba manual recargar durante una ventana; HC-05-09-06 cierre terminal/metadatos, con tests transaccionales de pausa abierta, `not_reached`, repetición y cierre anticipado, más prueba manual revisar/cerrar/recuperar. Correcciones sin dispositivo y retirada del store/sincronización se especificarán después de validar el flujo online y resolver datos heredados.

## Límites ya decididos y alcance posterior

- Los timestamps se limitan a `startedAt`/`finishedAt`, intervalos de pausa y un único `active_timer` para la ancla/fase que no se deriva. Duración y expiración se calculan desde snapshot, hora actual y pausas. HC-05-09-05 debe demostrar por modalidad que el ancla es necesaria antes de persistirla.
- No se incorpora `GET /:id`; HC-05-09-02 usa `/open` para ejecución en curso. Si la vista de historial no permite resolver una corrección cerrada, documentar esa necesidad concreta antes de proponer una lectura adicional.
- La protección de IndexedDB es lectura, comparación y exportación/revisión explícita; no sincronización automática ni borrado. HC-05-09-03 no retira el store.
- HC-06/HC-07 no están especificadas en el repositorio revisado; su integración futura no bloquea las decisiones de esta especificación.
