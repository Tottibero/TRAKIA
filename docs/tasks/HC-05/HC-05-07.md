# HC-05-07 — Correcciones auditables y regresión final

## Identificación

- **Bloque:** HC-05
- **Estado:** completada
- **Especificación aprobada:** solicitud del propietario del 2026-11-15.

## Especificación aprobada

### Objetivo

Permitir corregir resultados de ejecuciones cerradas, conservar los valores previos y corregidos en PostgreSQL y verificar la regresión final del bloque HC-05.

### Alcance

- Añadir correcciones online posteriores al cierre dentro del módulo `workouts`, reutilizando `WorkoutCorrection`, `CorrectResultOperation` y `WorkoutSyncResponse`.
- Corregir una métrica admitida o el ejercicio realmente utilizado, validando resultado, snapshot, ejercicio/alternativas, dispositivo, secuencia y valores anteriores.
- Persistir operación de corrección e historial junto al resultado efectivo de forma atómica en la fila de ejecución.
- Hacer idempotente el reintento HTTP por `operationId` y contenido exacto; mantener estado `completed`, cierre original y reserva global.
- Añadir en la vista de ejecución cerrada una edición sencilla de resultados, confirmada por el servidor antes de actualizar el resultado visible.
- Conservar el borrador ante errores de red o validación y la misma identidad de operación ante reintento ambiguo, sin cola offline.
- Ejecutar pruebas unitarias, web, API, integración PostgreSQL aislada, regresión existente, checks del proyecto y auditoría arquitectónica.
- Documentar pruebas/cobertura, limitaciones y smoke test manual pendiente; cerrar la ficha tras aceptación del propietario.

### Exclusiones

Correcciones offline o multi-dispositivo, modificación del snapshot, edición de `activeSeconds`/`windowProgressSeconds`, tablas de eventos, event sourcing, plataforma genérica de auditoría, workers, coordinación entre pestañas, cambios al cierre original o al índice de reserva.

### Dependencias

HC-05-01 a HC-05-06; contratos de ejecución, corrección y sincronización de HC-02; feature `workout-execution`; módulo API `workouts`; ADR-015 y `docs/architecture/module-conventions.md`.

### Archivos o módulos afectados

- `apps/api/src/modules/workouts/`, migración aditiva y tests API/integración.
- `apps/web/src/features/workout-execution/` y tests de UI/sincronización.
- Documentación HC-05, `docs/domain/workout-synchronization.md` y `docs/progress.md`.
- Contracts solo ante incompatibilidad demostrada; no se prevé ampliar los esquemas.

### Criterios de aceptación

1. Una ejecución `completed` permite seleccionar y corregir un resultado registrado.
2. Backend comprueba cuenta y dispositivo propietario, estado cerrado, resultado perteneciente a la ejecución, snapshot, compatibilidad del campo, valor `before` vigente y secuencia.
3. Corrección e historial se guardan atómicamente; una corrección desactualizada o contradictoria no cambia el resultado ni el historial.
4. Repetir una operación idéntica devuelve `already_applied`; reutilizar identidad con otro contenido no aplica escrituras.
5. El resultado corregido queda visible solo tras `applied`/`already_applied`; los errores conservan el formulario y permiten reintentar la misma operación.
6. El estado, fecha y sobre del cierre no cambian; la reserva global sigue liberada.
7. No se envían correcciones estando offline ni se implementa cola de correcciones.
8. Tests específicos cubren métricas, ejercicio, valores desactualizados, identidad/replay, atomicidad, pertenencia, dispositivo, estado y errores de interfaz.
9. Integración confirma previamente que `current_database() = trakia_test`; no se accede a `trakia_dev` ni se inicia Docker.
10. `pnpm check`, `pnpm architecture:check`, `pnpm format:check` y `git diff --check` pasan; revisión arquitectónica independiente queda registrada.

### Pruebas previstas

- Contratos existentes sin cambios; unitarias de aplicación/API para validación, secuencia, corrección y reintentos.
- Controlador HTTP para autenticación, esquema y respuestas; integración PostgreSQL para atomicidad, rollback, reintento, contradicciones y estado/reserva.
- Web para edición móvil, campos compatibles, error conservando formulario, estado offline y replay con identidad estable.
- Regresión en suites existentes de importación, calendario, ejecución guiada, recuperación, resultados y cierre; no duplicar casos ya cubiertos.
- `pnpm check`, `pnpm architecture:check`, `pnpm format:check`, `git diff --check`.
- Smoke manual en móvil con JSON válido que cubra fuerza, circuito/superserie, AMRAP e intervalos; pendiente y sin importar hasta autorización/ejecución real.

## Ejecución y resultados

### Resumen de implementación

Se añadió `POST /workouts/executions/:executionId/corrections`, usando el contrato de operación existente. La operación exige ejecución cerrada, dispositivo original, resultado existente, secuencia consecutiva y valores anteriores vigentes. El resultado efectivo y el sobre de corrección se guardan juntos en una transacción; los reintentos idénticos responden `already_applied`.

La migración aditiva `AddWorkoutExecutionCorrectionOperations1795305600000` crea `correction_operations jsonb NOT NULL DEFAULT []`. No se creó tabla de eventos. Se conserva exactamente el sobre de cierre y la ejecución permanece `completed`.

La vista cerrada permite editar métricas compatibles y ejercicio entre las alternativas del snapshot. Solo ofrece enviar con conexión; espera confirmación antes de actualizar el valor visible, conserva formulario e identidad durante errores/reintentos y persiste localmente las correcciones confirmadas sin modificar el cierre original.

### Archivos realmente modificados

API: módulo `workouts` (entidad, controlador y servicio), migración aditiva y pruebas de servicio, controlador e integración.

Web: cliente de ejecución, store IndexedDB, composable de sesión, vista cerrada y pruebas de edición/persistencia.

Documentación: esta ficha, índice HC-05, `ejecutor-diseno.md`, `docs/domain/workout-synchronization.md` y `docs/progress.md`. No se cambiaron contracts: los esquemas de corrección y sincronización existentes cubren el alcance.

### Pruebas ejecutadas y resultados

- `pnpm check`: satisfactorio. Incluye lint, `format:check`, typechecks, `architecture:check` (180 módulos sin violaciones), 87 pruebas API, 55 pruebas web y builds de contracts/web/API.
- `pnpm test:integration`: satisfactorio. El preflight verificó `current_database() = trakia_test`; aplicó únicamente la migración nueva y pasó el runner completo, incluida la integración de ejecución con corrección aplicada/repetida, valor desactualizado, rollback forzado y preservación de cierre/reserva. No se inició Docker ni se accedió a `trakia_dev`.
- `pnpm architecture:check`: satisfactorio, 180 módulos sin violaciones. La primera ejecución aislada dentro del sandbox falló en la fixture de `dependency-cruiser`; repetida fuera del sandbox pasó. El mismo check también pasó dentro de `pnpm check`.
- `pnpm format:check` y `git diff --check`: satisfactorios.
- Pruebas web nuevas: construcción de cambios métricos/ejercicio, validación de valores y actualización local confirmada conservando el sobre original del cierre.
- Tests API nuevos: autenticación/validación HTTP, secuencia, idempotencia, replay contradictorio, métricas/ejercicio, stale `before` y dependencia pendiente. Integración PostgreSQL cubre persistencia, cierre inmutable y rollback.
- Detector Impeccable sobre la vista cerrada: sin hallazgos deterministas.

La regresión existente ejecutada cubre importación JSON y handoff, calendario/detalle, inicio/recuperación, series/alternativas, circuitos/AMRAP/intervalos, temporizadores/pausas, IndexedDB, revisión/cierre, sincronización y reserva. No se duplicaron esos casos.

La integración de correcciones prueba el servicio con PostgreSQL y el controlador por tests unitarios, no un recorrido HTTP completo de corrección.

### Desviaciones justificadas

Las correcciones son online y no se encolan. La identidad de la operación se conserva en la vista si la respuesta HTTP es ambigua; no se añade una cola offline ni coordinación entre dispositivos. No se corrigen `activeSeconds` ni `windowProgressSeconds`, campos que no admite `WorkoutCorrectionChange`.

### Incidencias y riesgos pendientes

Queda pendiente el smoke test manual integral en móvil con un JSON válido que cubra fuerza, circuito/superserie, AMRAP e intervalos. No se importaron datos de prueba. La edición requiere el dispositivo original y no es recuperable si se borra el almacenamiento local antes de volver a abrir la ejecución; el servidor conserva las correcciones, pero esta UI sigue leyendo la copia local establecida por HC-05.

### Revisión arquitectónica

- **Resultado:** favorable; sin incumplimientos ni recomendaciones pendientes.
- **Ámbito:** cambios API de `workouts` y migración, feature `workout-execution`, pruebas y documentación HC-05-07. Revisado de forma independiente contra ADR-015 y `module-conventions.md`.
- **Reglas aplicables:** `ARCH-API-004`, `ARCH-API-006`, `ARCH-API-007`, `ARCH-WEB-001` a `ARCH-WEB-004`, `ARCH-ALL-001` a `ARCH-ALL-003`.
- **Evidencia:** controlador valida el contrato y delega al servicio del mismo módulo; bloqueo y persistencia permanecen en `workouts`; columna aditiva propiedad de la ejecución; contracts siguen neutrales y sin cambios; web consume API compartida; no se añadieron módulos, eventos, tablas ni abstracciones genéricas. `pnpm architecture:check` pasó con 180 módulos.
- **Hallazgos y resolución:** ninguno. La duplicación entre resultado efectivo e historial conserva la intención de auditoría; no se encontró duplicación accidental de sincronizadores ni estado innecesario.

### Revisión y aceptación

- **Resultado:** completada; aceptación del propietario concedida explícitamente para el cierre local.
- **Evidencia de aceptación:** `pnpm check`, `pnpm architecture:check`, `pnpm format:check`, `git diff --check`, pruebas API/web e integración PostgreSQL en `trakia_test` satisfactorias; auditoría arquitectónica independiente favorable y sin recomendaciones pendientes.
- **Limitación aceptada:** el smoke test integral manual móvil sigue pendiente y no se importaron datos de prueba. La corrección en la UI requiere el dispositivo original y la copia local de ejecución; no hay cola offline ni recuperación de esa pantalla tras borrar el almacenamiento local. No bloquea este cierre.

Flujo aplicado: `$trakia-task HC-05-07` dejó la tarea en revisión; `$trakia-architecture check HC-05-07` registró la auditoría independiente; la autorización explícita del propietario para `$trakia-git commit HC-05-07` acepta el cierre definitivo.
