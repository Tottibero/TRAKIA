# HC-05-09-04c — Pausa y reanudación online

## Identificación

- **Bloque:** HC-05
- **Estado:** completada
- **Tipo:** persistencia y transiciones online de pausa/reanudación.

## Especificación aprobada

### Objetivo

Implementar pausa y reanudación de una ejecución online usando PostgreSQL como única fuente de verdad y los contratos y flujo online de HC-05-09-04a/04b.

### Alcance

- Persistir los intervalos de pausa con timestamps del servidor en la ejecución existente.
- Añadir operaciones autenticadas, transaccionales e idempotentes para pausar y reanudar.
- Descontar las pausas del tiempo efectivo de trabajo y del descanso; conservar el ancla del temporizador.
- Recuperar estado y pausas desde PostgreSQL tras recarga y desde otra sesión autenticada de la misma cuenta.
- Presentar «Pausado» y «Reanudar», manteniendo ejercicio y objetivos visibles; el servidor confirma antes del cambio deportivo de UI.
- Añadir migración aditiva, pruebas de contratos, API, integración PostgreSQL y flujo web.
- Actualizar esta ficha, el índice HC-05 y `docs/progress.md`; terminar `completada` tras la aceptación manual.

### Exclusiones

- IndexedDB, colas offline, ticks persistidos, tiempo restante persistido o resultados ficticios.
- Cambios de modelo deportivo de resultados, correcciones o cierre fuera de las precondiciones necesarias para impedir transiciones mientras está pausado.
- Otras modalidades distintas de fuerza online, rediseño general, Docker, commit, push, PR y merge.

### Dependencias

- HC-05-09-04, HC-05-09-04a y HC-05-09-04b.
- `WorkoutPause`, estado de ejecución y `activeTimer` de contratos existentes; módulo `workouts` y API autenticada.
- ADR-015 y `docs/architecture/module-conventions.md`.

### Archivos o módulos afectados

- Contracts: `packages/contracts/src/workout-executions/workout-execution-pause.ts`, `workout-execution-start.ts`, `index.ts` y pruebas.
- API: entidad, servicio y controlador de `apps/api/src/modules/workouts/`; migración aditiva en `apps/api/src/database/migrations/`; pruebas unitarias e integración HTTP.
- Web: cliente API, `online-strength-flow.ts`, `OnlineStrengthExecutionView.vue` y pruebas del flujo.
- Documentación: esta ficha, `docs/tasks/HC-05/README.md` y `docs/progress.md`.

### Criterios de aceptación

1. Una ejecución abierta puede pausarse durante trabajo o descanso; no se crean intervalos duplicados por doble pulsación/reintento.
2. Reanudar cierra la pausa identificada y reintentos con la misma identidad son idempotentes; transiciones obsoletas responden conflicto.
3. Trabajo efectivo y descanso restante excluyen el tiempo pausado y conservan sus anclas.
4. Recargar o consultar desde otra sesión autenticada recupera `status`, intervalos y temporizador desde PostgreSQL.
5. Mientras está pausado se bloquea iniciar otra serie y la vista muestra «Pausado» y «Reanudar» sin ocultar ejercicio/objetivos.
6. Errores HTTP no cambian el estado deportivo visible; el cierre y los resultados confirmados no se alteran.
7. No se persisten ticks ni tiempo restante y no se utiliza almacenamiento offline.
8. `pnpm check`, `pnpm architecture:check`, integración PostgreSQL en `trakia_test` con `current_database()` verificado y `git diff --check` pasan; el usuario confirma que la prueba manual de pausas y reanudaciones funcionó correctamente.

### Pruebas previstas

- Pausa de trabajo y descanso, reanudación y cálculo efectivo correcto.
- Recuperación pausada por `GET /open`, incluido acceso desde otra sesión autenticada.
- Reintentos/doble pulsación, conflictos de pausa obsoleta y fallos HTTP sin estado falso.
- Inicio de serie bloqueado durante pausa; cierre/resultados conservados.
- Integración PostgreSQL solo en `trakia_test`, comprobando `SELECT current_database()` antes de migrar y de ejecutar la integración.
- `pnpm check`, `pnpm architecture:check` y `git diff --check`.

## Ejecución y resultados

### Resumen de implementación

Se añadieron pausas y reanudaciones autenticadas en `workouts`, usando intervalos JSONB y timestamps PostgreSQL. Los cálculos de trabajo y descanso excluyen pausas sin cambiar las anclas; la vista recupera el estado pausado y solo cambia tras confirmar el servidor.

### Archivos realmente modificados

- Contracts: contratos HTTP de pausa/reanudación y recuperación de estados pausados.
- API: entidad, servicio, controlador y migración aditiva `AddWorkoutExecutionPauses1795651200000`.
- Web: cliente de API, flujo online y vista de fuerza; pruebas del flujo con fallos HTTP.
- Tests: controladores, contratos, esquema aislado PostgreSQL e integración HTTP concurrente.
- Documentación: ficha HC-05-09-04c, índice HC-05 y progreso.

### Pruebas ejecutadas y resultados

- `pnpm check`: satisfactorio; lint, formato, typecheck, arquitectura incluida, 95 pruebas API, 90 pruebas web y builds.
- `pnpm architecture:check`: satisfactorio por separado; 205 módulos, sin violaciones. Requirió salir del sandbox porque el fixture hijo de dependency-cruiser terminaba sin salida dentro de él.
- `pnpm test:integration`: satisfactorio en PostgreSQL. El runner verificó `current_database() = trakia_test`; aplicó la migración de pausas y en la ejecución final informó que no quedaban migraciones pendientes. Pasó la suite, incluida la integración HTTP.
- PostgreSQL de desarrollo: se confirmó que el 500 del calendario se debía a la ausencia de `workout_executions.pauses` en `trakia_dev`. Tras comprobar `current_database() = trakia_dev` y revisar pendientes, se aplicó `AddWorkoutExecutionPauses1795651200000`; la consulta posterior confirmó columna y migración aplicadas. El GET autenticado `/api/training-plans/calendar?from=2026-11-16&to=2026-11-22` devolvió HTTP 200.
- Integración HTTP puntual tras añadir doble pulsación concurrente: satisfactoria; sin duplicados, inicio bloqueado durante pausa, recuperación con otro token de la cuenta, 10,02 s efectivos tras una pausa simulada de 10 s y descanso todavía pendiente tras descontar la pausa.
- `impeccable detect` sobre `OnlineStrengthExecutionView.vue`: sin hallazgos.
- `git diff --check`: satisfactorio.

### Desviaciones justificadas

La reanudación identifica la pausa por su `startedAt` asignado por servidor; esto permite reconocer reintentos incluso después de perder la respuesta y rechazar identidades obsoletas sin añadir una tabla de operaciones.

### Incidencias y riesgos pendientes

Las primeras ejecuciones de integración detectaron que el esquema aislado aún no aplicaba la migración nueva y que `/open` rechazaba `status: paused`; se actualizaron el fixture y el contrato de recuperación y las ejecuciones posteriores pasaron. El contenedor API estaba sano pero su base `trakia_dev` no había recibido la migración, lo que causaba el 500 del calendario; migrar esa base aditiva resolvió el error. La aceptación manual comunicada cubre la prueba de pausas y reanudaciones; no se atribuye a ella una verificación independiente de cada escenario enumerado.
