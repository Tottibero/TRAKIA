# HC-05-10-02b — Validación autoritativa de fecha de inicio

## Identificación

- **Bloque:** HC-05
- **Estado:** completada

## Especificación aprobada

### Objetivo

Restringir de forma autoritativa el inicio de sesiones planificadas a su fecha civil programada en `Europe/Madrid`, tanto en la interfaz como en `POST /workouts/executions/start`.

### Alcance

- Compartir en frontend la misma función civil de `Europe/Madrid` entre calendario y detalle, sin depender de la zona horaria del navegador.
- Comparar la fecha planificada con la fecha actual obtenida del reloj del servidor.
- Responder con un error de dominio/HTTP identificable cuando un inicio nuevo llega fuera de fecha; no guardar ejecución ni proteger/reservar la sesión.
- Mantener la idempotencia: una solicitud ya iniciada válidamente se reproduce aunque haya cambiado el día.
- Permitir continuar, pausar, reanudar, guardar resultados y finalizar ejecuciones abiertas sin revalidar la fecha planificada.
- Conservar el comportamiento para sesiones sin fecha y las reglas independientes de actividades voluntarias.
- Documentar la relación con la semana flexible: navegar por la semana no habilita iniciar las sesiones de otros días.
- Actualizar esta ficha, HC-05-10-02, índice HC-05 y progreso; ambas fichas permanecen `en revisión` hasta smoke manual.

### Exclusiones

- Cambios de planificación, resultados existentes, temporizadores deportivos o actividades voluntarias.
- Migraciones, almacenamiento local, servicios de reloj nuevos o infraestructura.
- Commit, push, PR o merge.

### Dependencias

- HC-05-10-02, cuyo rediseño está aceptado visualmente y cuya interfaz ya oculta el inicio fuera de fecha.
- Política de calendario de HC-04: fecha civil actual en `Europe/Madrid`.
- ADR-015 y `docs/architecture/module-conventions.md`.

### Archivos o módulos afectados

- Función de fecha compartida del frontend, calendario semanal y feature `workout-execution`.
- Servicio/controlador de inicio en `workouts`, validación de errores HTTP y contratos de error de ejecución.
- Pruebas unitarias web/API e integración HTTP/PostgreSQL.
- Esta ficha, HC-05-10-02, índice HC-05 y `docs/progress.md`.

### Criterios de aceptación

1. Sesiones de ayer y mañana se rechazan; la sesión de hoy se inicia usando `Europe/Madrid` tanto desde frontend como desde API.
2. La API devuelve `409` con código de dominio estable para un inicio directo fuera de fecha y no crea una ejecución ni protege la sesión.
3. Un reintento con el mismo `requestId` devuelve la ejecución ya iniciada aunque ocurra después de medianoche.
4. Recuperar y operar una ejecución abierta y consultar una ejecución completada no vuelven a validar la fecha planificada.
5. Los cambios de DST de Madrid y navegadores en otra zona horaria no cambian la fecha civil comparada.
6. Las sesiones sin fecha y las actividades voluntarias conservan sus reglas actuales.
7. `pnpm check`, `pnpm architecture:check`, integración PostgreSQL aislada en `trakia_test` y `git diff --check` pasan.
8. HC-05-10-02 y esta ficha quedan `en revisión` hasta smoke manual del propietario; sin operaciones Git remotas o commit.

### Pruebas previstas

- Unitarias de comparación: ayer/hoy/mañana, replay tras medianoche, ausencia de fecha y operaciones de ejecución abierta.
- Web: zona de navegador distinta de Madrid y medianoche/DST de 23 y 25 horas.
- HTTP autenticado: intento directo fuera de fecha, respuesta de dominio y ausencia de fila, además de inicio válido.
- Integración PostgreSQL sobre `trakia_test`, verificando explícitamente `SELECT current_database()` con el mismo datasource.
- `pnpm check`, `pnpm architecture:check` y `git diff --check`.

## Ejecución y resultados

### Resumen de implementación

El detalle y el calendario usan una utilidad civil compartida de `Europe/Madrid`, independiente de la zona del navegador; el temporizador del permiso vence en la siguiente medianoche madrileña y conserva los días DST de 23/25 horas. El inicio API revisa el día del servidor antes de bloquear y vuelve a comprobarlo tras recargar la sesión bajo los locks compartidos. Las solicitudes idempotentes existentes se resuelven antes de esta regla. Una fecha ausente no se inventa ni causa el rechazo por fecha; los flujos voluntarios siguen separados. Los inicios fuera de día devuelven `409 PLANNED_DATE_MISMATCH` y no crean una ejecución.

### Archivos realmente modificados

- Frontend: `apps/web/src/shared/utils/madrid-civil-date.*`, calendario (`calendar-dates.js`) y feature `workout-execution` (helper, composable y acción).
- API/contracts: `apps/api/src/shared/madrid-civil-date.ts`, servicio/controlador de `workouts`, reutilización en revisión de importación y código de error Zod.
- Regresiones: `apps/web/test/planned-session-start.test.mjs`; pruebas API unitarias/controlador e integración HTTP/PostgreSQL.
- Documentación: HC-05-10-02, esta ficha, `docs/tasks/HC-05/README.md` y `docs/progress.md`.

### Desviaciones justificadas

No se añadieron migraciones ni almacenamiento. `PLANNED_DATE_MISMATCH` amplía únicamente el enum compartido de errores para permitir una respuesta HTTP de dominio estable; no cambia el formato de inicio ni el modelo deportivo.
