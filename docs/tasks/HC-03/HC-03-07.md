# HC-03-07 — API HTTP y experiencia frontend del importador JSON

## Identificación

- **Bloque:** HC-03
- **Estado:** completada
- **Aprobación de esta especificación:** aprobada por el propietario para implementación.
- **Límite:** no ampliar el alcance aprobado descrito en esta ficha.

## Especificación aprobada

### Objetivo

Exponer por HTTP los casos de uso de revisión y confirmación ya implementados, y ofrecer en Vue un flujo móvil primero para seleccionar, validar, revisar y confirmar un documento `TrainingPlanImportV1`. El flujo debe explicar cambios, datos conservados y conflictos antes de escribir, y reutilizar la identidad visual observable de TRAKIA mediante tokens semánticos reutilizables. No cambia las reglas de importación ni el contrato JSON v1.

### Alcance

- Crear los contratos HTTP públicos de revisión, confirmación y error en `@trakia/contracts`, reutilizando `TrainingPlanImportV1Schema`, `TrainingPlanDefinitionSchema` e `ImportValidationIssueSchema` sin duplicarlos ni alterarlos.
- Añadir al módulo `training-plan-imports` los endpoints HTTP que adaptan peticiones/respuestas a `TrainingPlanImportReviewService` y `TrainingPlanImportConfirmationService`. El controlador solo valida el transporte, obtiene el principal autenticado y traduce resultados/excepciones; no incorpora reglas deportivas ni persistencia.
- Implementar una feature web protegida que permita elegir un archivo `.json`, leerlo como texto, parsearlo sin evaluar código, validar localmente y solicitar la revisión del servidor. La validación del servidor sigue siendo obligatoria.
- Presentar resultados separados: incidencias estructurales del documento, cambios (`created`, `modified`, `unchanged`, `preserved`), conflictos persistidos y estado confirmable. Mostrar explícitamente que los elementos omitidos se conservan y que no hay eliminaciones implícitas.
- Permitir confirmar únicamente después de una revisión confirmable y una acción explícita del usuario. Un conflicto bloquea la confirmación completa. Tras éxito, error recuperable o revisión vencida, mostrar un estado claro y ofrecer volver a revisar sin perder silenciosamente el archivo en memoria.
- Definir estados de interfaz: `empty`, `reading`, `invalid-json`, `invalid-document`, `reviewing`, `reviewed-with-conflicts`, `ready-to-confirm`, `confirming`, `confirmed`, `unchanged`, `stale-or-expired` y `request-error`. Cambiar el archivo invalida la revisión y el token anteriores.
- En confirmación, generar un `operationId` UUID nuevo por operación y conservarlo para reintentos de la misma petición mientras la vista siga activa. Nunca generar un ID distinto para resolver un resultado de red incierto. No persistir documento, token ni operación en `localStorage`/`sessionStorage`.
- Integrar la ruta con la autenticación existente y enlazarla desde la pantalla de inicio. Usar el cliente HTTP común, que ya envía cookies, credenciales y el encabezado CSRF para `POST`.
- Establecer tokens CSS semánticos globales mínimos para la feature, tomando sus valores de la interfaz existente. No crear un sistema de componentes ni rehacer la pantalla de acceso.

### Diseño UX/UI aplicado a la propuesta

Por ello esta propuesta trata `style.css`, `HomeView.vue` y `LoginView.vue` como autoridad para una extensión; no crea una identidad nueva ni atribuye decisiones visuales aprobadas que no constan en el repositorio.
- El modo de uso es **Operate**: una herramienta privada y repetida. La pantalla es una secuencia de tarea compacta, con controles previsibles, resumen escaneable y errores vinculados a la acción. No se plantea una landing ni una cuadrícula promocional.
- Las búsquedas de UI/UX Pro Max para el producto devolvieron patrones de conversión/marketing y luego un estilo lúdico infantil. Se comprobaron y se descartaron por no encajar con el producto ni la identidad vigente; no se persisten sus paletas ni patrones. Su consulta de UX respalda etiquetas visibles y un resumen de errores localizable por teclado; la consulta Vue se toma como referencia, no como mandato para añadir una librería de formularios a este flujo de archivo.
- El análisis con `ui-design-system` parte de los colores repetidos en `apps/web/src/style.css`: fondo `#10110f`, superficie `#191a17`, texto `#f5f5f4`, texto secundario `#a8a8a2`, borde `#393b35` y acento `#bef264`/hover `#d9f99d`. La especificación propone nombrarlos como variables semánticas CSS y añadir tokens de estado solo con contraste verificado; no cambia sus valores base ni genera una paleta paralela.

### Contratos HTTP propuestos

Prefijo global actual: `/api`. Las peticiones usan `Content-Type: application/json` y las rutas requieren autenticación.

**Revisión sin escrituras**

```http
POST /api/training-plan-imports/reviews
```

```json
{ "document": { "format": "trakia.training-plan", "version": 1, "exercises": [], "plan": {} } }
```

El objeto es esquemático; los datos deben cumplir `TrainingPlanImportV1Schema`.

Respuesta `200`: `{ valid, confirmable, issues, changes, conflicts, proposal?, reviewToken?, reviewExpiresAt? }`. `proposal` es la definición combinada que el usuario debe revisar, sin UUID ni versión interna. Solo se devuelve `reviewToken` y `reviewExpiresAt` cuando el documento es válido y no hay conflictos. Una estructura JSON válida en HTTP pero inválida para el contrato devuelve `200`, `valid: false`, todas las incidencias normalizadas y ningún token. Un conflicto persistido devuelve `200`, `valid: true`, `confirmable: false`, conflictos y ningún token.

**Confirmación atómica e idempotente**

```http
POST /api/training-plan-imports/confirmations
```

```json
{
  "document": { "format": "trakia.training-plan", "version": 1, "exercises": [], "plan": {} },
  "reviewToken": "<token opaco de la revisión>",
  "operationId": "<UUID generado por el cliente>"
}
```

El documento sigue siendo el objeto validado por `TrainingPlanImportV1Schema`; los valores abreviados de estos ejemplos no constituyen fixtures válidas.

Respuesta `200`: `{ status: "confirmed" | "unchanged", operationId, changes }`. El controlador no expone IDs internos de persistencia. El mismo usuario, `operationId` y contenido repite el resultado registrado; una huella diferente devuelve conflicto. La repetición no vuelve a aplicar escrituras.

Los contratos compartidos deben concretar enums estables para `kind`, `status`, `resource` y códigos existentes: `EXERCISE_DEFINITION_CONFLICT`, `UNRESOLVED_PERSISTED_EXERCISE_KEY`, `EXERCISE_NOT_FOUND`, `INVALID_COMBINED_PLAN`, `PAST_SESSION_PROTECTED`, `SESSION_EXECUTION_PROTECTED`, `IDENTITY_TYPE_MISMATCH`, `OPERATION_ID_CONTENT_MISMATCH`, `STALE_IMPORT_REVIEW`, `STALE_PLAN_VERSION`, `CONCURRENT_CATALOG_OR_PLAN_CHANGE`, `INVALID_OR_EXPIRED_REVIEW_RECEIPT` e `IMPORT_CONFLICT`. Mantener `path` como segmentos string/índice numérico. Errores HTTP usan un código estable y, cuando corresponda, `issues` o `conflicts`; no incluyen stack traces, secretos ni mensajes de infraestructura. La interfaz muestra copy en español por código y conserva la ruta de campo para identificar el elemento afectado.

**Mapeo HTTP**

| Situación | Respuesta propuesta | Comportamiento frontend |
|---|---:|---|
| Revisión completada, con o sin incidencias/conflictos de dominio | 200 | Mostrar el resultado discriminado por `valid` y `confirmable`. |
| JSON HTTP malformado o envoltorio/petición ilegible | 400 | Error de transporte; no confirmar. El JSON del archivo se parsea localmente antes de enviar. |
| Falta autenticación | 401 | Usar la redirección existente a login y regresar a `/training-plans/import`. |
| CSRF/origen rechazado | 403 | Mensaje seguro; no reintentar automáticamente. |
| Documento inválido al confirmar | 422 | Mostrar incidencias y exigir una nueva revisión. |
| Token inválido/expirado, conflicto concurrente o `operationId` con otra huella | 409 | Invalidar la revisión y ofrecer revisar de nuevo; no confirmar automáticamente. |
| Cuerpo excede el límite aprobado | 413 | Explicar el límite y permitir elegir otro archivo. |
| Fallo inesperado | 500 | Mensaje genérico en español, conservar estado recuperable y no mostrar detalles internos. |

### Frontend móvil primero e identidad reutilizable

- Ruta privada propuesta: `/training-plans/import`, con enlace de acceso desde `HomeView.vue`.
- En móvil, un flujo de una columna: encabezado y progreso de tres pasos (archivo, revisión, confirmación), selector de archivo grande y etiquetado, resumen y CTA en el flujo normal. El selector nativo funciona sin drag-and-drop; no se depende de hover ni de controles pequeños. En pantallas anchas se puede ampliar el resumen en columnas, manteniendo el orden semántico y el mismo contenido.
- Aceptar solo `.json` y leer el contenido como texto UTF-8. Mostrar nombre y tamaño del archivo. Rechazar archivos vacíos o cuyo cuerpo serializado supere el límite común acordado antes de enviar. No ejecutar contenido ni enviar `multipart/form-data`; el backend recibe el objeto JSON.
- Los resultados muestran contadores y listas de creaciones, modificaciones, elementos sin cambios, elementos conservados y conflictos. Las incidencias y conflictos incluyen el mensaje español, el código de soporte y la ruta legible. El resumen de errores tiene encabezado enfocable y enlaces a elementos cuando exista un control correspondiente; no se comunica el error solo con color o toast.
- Revisión vencida o obsoleta requiere nueva consulta. El token no es renovable por el cliente; no ofrecer un botón que extienda sus quince minutos. Si falla la confirmación con resultado de red incierto, reintentar únicamente con el mismo `operationId`.
- Añadir variables semánticas a `:root` para fondo, superficie, texto, texto secundario, borde, acento, acento-hover y foco; conservar los valores observados. Los colores de error/advertencia/éxito deben pasar contraste de 4.5:1 para texto normal sobre cada superficie. No hacer una migración global de estilos fuera de lo necesario para compartir estos tokens.
- Español como idioma visible, estados de foco claros, teclado completo, etiquetas persistentes, foco gestionado al presentar errores, mensajes con `role="alert"`/`aria-live` apropiados, controles objetivo táctil de al menos 44 × 44 CSS px y respeto a `prefers-reduced-motion`.
- Mantener en memoria de la vista el archivo, la respuesta de revisión y el token. Un cambio de archivo o reinicio de la vista limpia token/resultado; ninguna navegación inicia confirmación.

### Decisiones aprobadas por el propietario

1. **Identidad `origin`:** fijar en el servidor el namespace constante `trakia-json-v1`, conforme al contrato existente; no añadir un campo al JSON ni aceptar un namespace del cliente.
2. **Detalle de revisión:** exponer la propuesta combinada sin IDs internos y un resumen/detalle sencillo a partir de los cambios existentes (`kind`, `key`, `path`, `status`), sin producir un diff de valores que el servicio no ofrece.
3. **Límite de carga:** máximo de 1 MiB para el cuerpo UTF-8 serializado, medido en cliente y API, con el límite del parser configurado explícitamente.

### Criterios de aceptación

1. La ficha aprobada mantiene exactamente las decisiones de HC-03-01 y HC-02; no cambia el contrato JSON v1, los siete códigos ni las reglas de revisión/confirmación.
2. Las peticiones HTTP pasan el principal autenticado a los servicios existentes. `reviews` no escribe; `confirmations` delega atómicamente en el servicio existente. No hay reglas deportivas, acceso a repositorios ni detalles de persistencia en el controller.
3. Los contratos de transporte Zod son estrictos, exportados desde el punto público de `@trakia/contracts`, usan tipos inferidos y cubren estados válidos e inválidos. No exportan UUIDs/versiones internas innecesarias, secretos ni objetos de excepción.
4. Los siete códigos existentes y rutas de incidencias llegan íntegros a la interfaz. El documento inválido durante revisión no produce token; cualquier conflicto impide confirmación; un documento válido y confirmable sí entrega token y fecha de expiración del servidor.
5. `reviewToken` solo se presenta al usuario como revisión vigente y no se registra. La confirmación requiere el mismo documento/token, UUID `operationId` y acción explícita; duplicar clics no duplica solicitudes, y un reintento de resultado de red incierto conserva el ID.
6. Errores HTTP siguen el mapeo especificado, incluidos JSON malformado, autenticación, CSRF, validación al confirmar, token vencido/obsoleto, conflicto, límite de cuerpo y fallo 500 genérico. El cliente no muestra stack traces ni mensajes internos.
7. La experiencia funciona con teclado y lector de pantalla, ofrece selector táctil sin dependencia de drag-and-drop, conserva estados y acciones entendibles, y no confirma al cambiar archivo, navegar o volver de login.
8. El recorrido muestra claramente cambios, datos conservados y conflictos antes de confirmar; no permite confirmar con incidencias/conflictos y requiere nueva revisión tras expiración u obsolescencia. No se prometen bajas ni importación parcial.
9. El diseño empieza por 375 px y no requiere scroll horizontal en 320–375 px; se revisa también a 768, 1024 y 1440 px. Foco, contraste normal de al menos 4.5:1, objetivos táctiles de 44 × 44 CSS px y movimiento reducido se verifican en los elementos implementados.
10. Los tokens semánticos reflejan la paleta vigente del frontend y son reutilizables por otras features. No se adopta la paleta/patrón de UI/UX Pro Max cuando contradice esa identidad; no se rehace la app completa.
11. Se aplican las tres decisiones aprobadas sobre `origin`, detalle de revisión y límite de 1 MiB. Tras autenticación, el login regresa solo a una ruta local validada y nunca a un destino externo. Tras implementar y verificar, la tarea pasa a `en revisión` y queda sujeta a auditoría independiente.

### Corrección posterior: errores HTTP del frontend

- Se clasifica el error por estado HTTP antes de exponer incidencias: solo 400/422 muestran errores de validación; 401 redirige a login; 403 explica permisos; 404 identifica el endpoint/recurso; 409 invalida la revisión; 413 indica el límite; 5xx y fallos de red tienen mensajes propios. Las incidencias adjuntas a cualquier otro estado se descartan.
- El cliente HTTP compartido convierte rechazos de `fetch` y fallos al leer un cuerpo exitoso en `ApiNetworkError`, y conserva los errores de cancelación. El copy y las acciones son de la feature: elegir otro archivo tras validación, volver al inicio por permisos, volver a revisar conflictos y reintentar fallos transitorios. Los reintentos de confirmación mantienen su `operationId`.
- **Superada:** regresión Node incorporada a `pnpm check`: 8 casos para 400/422, 401, 403, 404 con incidencias engañosas, 409, 413, 5xx y conexión.
- **Superada con Node 26.13.0 y pnpm 12.19.0:** `pnpm check`; lint, formato, typecheck, arquitectura (123 módulos), 61 pruebas API, 8 regresiones web y builds completos.
- **Superada:** detector de Impeccable para la feature y tokens globales, sin hallazgos (`[]`); `git diff --check` limpio.
- **Auditoría arquitectónica del correctivo:** sin hallazgos. `ApiNetworkError` vive en el cliente transversal (`ARCH-WEB-003`); la clasificación y copy permanecen en la feature, sin dependencias entre features ni nuevas capas compartidas.
