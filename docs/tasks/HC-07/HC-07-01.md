# HC-07-01 — Catálogo versionado para planificación con ChatGPT

## Identificación

- **Bloque:** HC-07
- **Estado:** completada

## Especificación aprobada

### Objetivo

Establecer un catálogo JSON versionado que ChatGPT pueda consultar para generar planes, sin sustituir el catálogo PostgreSQL ni modificar el importador v1.

### Alcance

- Revisar el estado del repositorio y sus reglas arquitectónicas.
- Auditar `exercises` y `exercise_catalog_keys`.
- Consultar el catálogo de producción en solo lectura y sin exponer datos personales.
- Identificar ejercicios, claves múltiples, definiciones y referencias externas.
- Diseñar `data/exercise-catalog.json` conforme a las definiciones del contrato actual y conservar las claves estables existentes.
- Validar automáticamente el archivo con Zod y comprobar claves duplicadas y referencias externas.
- Documentar altas y prevención de divergencias con PostgreSQL.
- Preparar una prueba de importación con ejercicios conocidos y nuevos, sin modificar datos reales.

### Exclusiones

- No modificar `trakia.training-plan` v1, PostgreSQL de producción, el importador ni la ejecución.
- No crear migraciones, ejercicios presentados como existentes sin evidencia, servicios ni automatizaciones.
- No introducir una segunda fuente de verdad operativa.

### Dependencias

- `ExerciseDefinitionSchema` y `TrainingPlanImportV1Schema` de `@trakia/contracts`.
- Catálogo vigente de producción, consultado por un medio de solo lectura.
- ADR-003, ADR-004, ADR-012, ADR-015 y `docs/architecture/module-conventions.md`.

### Archivos o módulos afectados

- `data/exercise-catalog.json` y validación/pruebas deterministas en el workspace que ya contiene los contratos.
- Documentación del dominio y fichas/índices HC-07, `docs/tasks/README.md` y `docs/progress.md`.
- No se prevén cambios en API, persistencia, contratos de importación, web ni configuración de servicios.

### Criterios de aceptación

1. El JSON refleja solo ejercicios verificados, mantiene todas sus claves estables y respeta las definiciones aceptadas por `ExerciseDefinitionSchema`.
2. La validación Zod rechaza el formato/versión incorrectos, definiciones inválidas, claves duplicadas y referencias externas que infrinjan las reglas del contrato actual.
3. La prueba de importación combina ejercicios conocidos del catálogo y una definición nueva válida mediante el contrato actual, sin tocar datos reales ni cambiar el importador.
4. La documentación explica cómo añadir ejercicios y cotejar cambios con PostgreSQL, manteniendo el JSON como referencia informativa para planificación y PostgreSQL como fuente operativa.
5. No hay migraciones ni cambios en contrato `trakia.training-plan` v1, API de importación, ejecución o recursos de producción.

### Pruebas previstas

- Pruebas Zod de catálogo válido, estructura/versionado, claves duplicadas, referencias externas y catálogo inválido.
- Prueba determinista del documento de importación mixto conocido/nuevo con `TrainingPlanImportV1Schema`.
- Verificaciones pertinentes de contracts, `pnpm check`, auditoría arquitectónica independiente y `git diff --check`.
- Consulta SQL de solo lectura a producción para las dos tablas del catálogo, precedida por comprobación de `current_database() = 'trakia'`.

### Desviaciones justificadas

No se modificaron datos de producción, esquemas/contracts existentes, importador ni ejecución. La prueba mixta de `TrainingPlanImportV1Schema` usa una fixture sintética de prueba porque producción no contiene un ejercicio conocido; no se presenta esa fixture como dato real.

### Incidencias y riesgos pendientes

La consulta real no encontró ejercicios que incorporar. La prueba mixta usa fixtures sintéticas y no escribe a la base; ahora comprueba referencias efectivas desde una sesión y rechaza una clave inexistente. Tampoco había asociaciones multiclave que documentar; el procedimiento indica cómo preservar una relación multiclave si aparece en una futura exportación.
