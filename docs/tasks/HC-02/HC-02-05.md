# HC-02-05 — Contrato JSON de importación de planes

## Identificación

- **Bloque:** HC-02 — Dominio deportivo
- **Estado:** completada
- **Rama:** `feat/hc-02-domain-model`

## Especificación aprobada

### Objetivo

Implementar exclusivamente contratos TypeScript/Zod para validar documentos JSON autocontenidos y versionados de importación de planes de entrenamiento.

### Alcance

- Definir el sobre v1 `format: "trakia.training-plan"`, `version: 1`, `exercises` y `plan`, reutilizando los contratos de catálogo y planificación.
- Validar referencias internas, claves de ejercicios duplicadas y compatibilidad comprobable entre objetivos explícitos y métricas declaradas.
- Rechazar propiedades desconocidas en todos los niveles, sin duplicar los contratos de ejercicios o planificación.
- Definir incidencias de validación normalizadas con códigos estables, ruta de propiedades/índices y mensaje.
- Documentar las siete decisiones de importación, actualización conservadora y protección de sesiones, distinguiendo validación JSON de consultas futuras a datos persistidos.
- Añadir pruebas Vitest y exportar deliberadamente el contrato por `packages/contracts/src/index.ts`.
- Actualizar índices, resultados y progreso; dejar la tarea `en revisión` antes de la auditoría arquitectónica independiente.

### Exclusiones

No implementar lectura de archivos, límites físicos, endpoints, persistencia, consultas al catálogo, resolución de conflictos, creación/actualización/eliminación de datos, transacciones, sincronización, servicios, UI, integraciones externas ni motores deportivos. No ejecutar commit, push, PR o merge.

### Dependencias

- HC-02-01, HC-02-02, HC-02-02a, HC-02-03 y HC-02-04; en particular, los contratos públicos de `exercises` y `training-plans`.
- ADR-015, `docs/architecture/module-conventions.md`, `docs/domain/training-plans.md` y `docs/domain/workouts.md`.

### Archivos o módulos afectados

- `packages/contracts/src/training-plan-imports/` y `packages/contracts/src/index.ts`.
- Contrato público de ejercicios solo en lo necesario para hacer estrictas sus definiciones y referencias reutilizadas.
- `docs/domain/training-plan-imports.md`, `docs/README.md`, esta ficha, `docs/tasks/HC-02/README.md` y `docs/progress.md`.

### Criterios de aceptación

1. El documento v1 es público, autocontenido, estricto y no incluye modo de operación ni UUID internos.
2. Todas las referencias de ejercicios del plan están definidas en el documento; las claves de definición no se duplican y pueden existir definiciones no usadas.
3. Se valida la compatibilidad de objetivos explícitos que puede determinarse sin seleccionar alternativas en ejecución ni consultar datos externos.
4. Las claves desconocidas se rechazan en el sobre, definiciones externas, planificación y estructuras anidadas.
5. El contrato de incidencias usa códigos acotados documentados y rutas tipadas con segmentos numéricos.
6. La documentación distingue lo validable en el JSON de las decisiones que requieren consultar persistencia; incluye conservación de ausentes y protección de sesiones iniciadas/cerradas.
7. Las pruebas cubren los casos enumerados en la especificación del propietario y se conservan las suites de contratos existentes.
8. No se implementan operaciones de importación ni se amplía el alcance funcional.

### Pruebas previstas

- Fixtures completos para documentos válidos y casos inválidos de estructura, referencias, duplicados, objetivos, fechas y propiedades desconocidas.
- Contrato de incidencias y exportaciones públicas.
- `pnpm check`, `pnpm architecture:check`, `pnpm --filter @trakia/contracts test` y `git diff --check`, usando Node/pnpm fijados por el repositorio.
- `$trakia-architecture check HC-02-05` como paso independiente posterior.

## Ejecución y resultados

### Resumen de implementación

Implementado el esquema público v1 mediante los contratos existentes de ejercicios y planificación. Valida claves duplicadas, referencias internas de bloques y fases, y compatibilidad de objetivos explícitos con las métricas declaradas. Las definiciones de ejercicios y referencias externas, así como los objetos de planificación, rechazan claves desconocidas. Las incidencias tienen códigos acotados y rutas tipadas; no se añadió transformación integral de errores Zod ni operaciones de importación.

### Archivos realmente modificados

- `packages/contracts/src/training-plan-imports/training-plan-import.ts` y `import-validation-issue.ts`: esquemas y tipos del sobre y las incidencias.
- `packages/contracts/src/training-plan-imports/training-plan-import.spec.ts`: fixtures completos y pruebas Vitest.
- `packages/contracts/src/exercises/exercise.ts`: modo estricto para definiciones y referencias externas reutilizadas.
- `packages/contracts/src/index.ts` y `packages/contracts/package.json`: exportaciones públicas y suite de contratos.
- `docs/domain/training-plan-imports.md`, `docs/README.md`, `docs/tasks/HC-02/README.md`, `docs/progress.md` y esta ficha.

### Desviaciones justificadas

Se aplicó `.strict()` al contrato reutilizado de ejercicios y a sus referencias externas, en lugar de mantener una copia específica para importación. El cambio es necesario para rechazar propiedades desconocidas en esas estructuras sin duplicar los esquemas. Los ajustes por serie/ronda se comprueban contra todas las opciones declaradas, pues el JSON no fija qué alternativa se seleccionará; no se añadió lógica de selección.

### Incidencias y riesgos pendientes

El permiso de `packages/contracts/dist/training-plan-imports` quedó corregido y pertenece a `tottibero:tottibero`; `pnpm check` y la suite de contracts compilaron y pasaron. No hay incidencias de verificación pendientes. No se ejecutaron operaciones contra persistencia. La conversión exhaustiva de errores Zod y las comparaciones de claves/definiciones con datos persistidos quedan para fases posteriores.
